## 1. 마일스톤

각 단계는 **혼자서 돌아가는 결과물**로 끝난다. 완료 기준을 통과해야 다음으로 간다. 실제 게임 검증은 마지막까지 기다리지 않고 M1부터 레포 밖에서 계속한다.

| 단계 | 만드는 것 | 완료 기준 |
|---|---|---|
| **M0a 실행 의미** | 모노레포, CI(라이선스 검사 포함), 메타스키마, 그래프 로더·실행 전 검증, 실행 의미(판정·반복·순수 노드·`$link`·재시도), 흐름·값·판정 노드. 한 프로세스 안에서 가짜 캡처·입력으로 실행 | 판정 순서표 전체, "반복 안에서 변수를 바꾸면 다음 조건이 달라짐", "지난 반복 출력 참조 거부", "중첩 반복에서 올바른 done 진입", 재시도 시도 기록, 스키마 문서 예시 JSON 검증 통과 |

| **M3 기록·디버거** | 기록 뷰어(타임라인·스크린샷·서브그래프 펼치기·지난 성공과 비교), 브레이크포인트·Step Into/Over, 재개 시 재검증, 실패 시 영상 보관(`video: failed_only`) | 실패 실행을 뷰어로 열어 실패 노드까지 한 번에 이동. 재개 후 대상이 사라졌으면 입력이 나가지 않음. 오래된 OCR로 분기하지 않음. 멈춘 시간이 두 타임아웃에서 빠짐. 성공한 실행의 영상은 지워지고, 기록 끈 구간은 영상에도 없음 |
| **M4 녹화** | 녹화기(사람 입력 → 노드), target 편집기 확장 | 예제 게임 로그인을 녹화한 그래프가 바로 재생 통과. 클릭 **이전** 프레임으로 target을 만든다. 툴 자신이 보낸 합성 입력은 녹화하지 않는다. 비밀번호 칸 입력은 글자 그대로 저장하지 않고 `$secret` 참조로 바꾸라고 요구한다 |
| **M5 Agent** | Kookabug MCP 서버(툴셋·연결별 상태), 에이전트 패널(ACP), Agent 판단 노드 2종 | 외부 에이전트가 MCP로 그래프를 만들고 실행하고 실패를 분석. 권한 거부가 집행됨. 같은 행위가 CLI·daemon(MCP)에서 같은 권한 판정 (daemon 어댑터가 주체·사람 확인 가능 여부를 공유 서비스에 그대로 넘김). UI와 에이전트가 동시에 고치면 늦은 쪽이 거부됨. 판단 노드의 에이전트에는 제어 도구가 주어지지 않음 |
| **M6 플러그인** | 설치, 잠금(해결된 의존성 환경까지), 공유/격리 venv, SDK 배포, UI 확장(JS) | 외부 레포의 샘플 플러그인이 설치·실행됨. 의존성이 충돌하는 두 플러그인이 격리됨. 설치 실패가 기존 환경을 깨지 않음. 다른 PC에서 잠금 파일로 같은 환경이 재현됨 |
| **M7 화면 지도** | 화면 지도 뷰어, Agent 탐색 결과 저장(`screens/_explored/`) | 예제 게임 탐색 결과가 화면 카드와 이동 그래프로 보이고, 사람이 확인해 `screens/`로 옮길 수 있음 |
| **MVP 검증** | 실제 게임 프로젝트에서 사용 (레포 밖) | 실제 게임의 스모크 테스트 몇 개를 무인으로 매일 돌림 |

- **예제 게임**: 레포 안에 작은 가짜 게임(`fixtures/sample-game`)을 둔다. 타이틀 → (점검 팝업) → 로그인 → 로비 → 월드 → 인벤토리. 실행 옵션으로 점검·로그인 실패·느린 로딩·해상도를 바꾼다. CI E2E와 문서 예시가 모두 이 게임을 쓴다. 헤드리스 CI용으로 화면 PNG와 장면 전이 표(`frames/scenario.json`, 게임 코드에서 생성)를 함께 둔다
- **실제 GPU 게임 검증**은 레포 밖에서 한다 (회사 게임 내용을 레포에 넣지 않는 원칙). 공개 검증용으로는 오픈소스 게임(예: SuperTuxKart)을 설치해 대상으로만 쓰고 레포에 넣지 않는다

## 2. 레포 구조

```
kookabug/
├─ apps/desktop/              Electron + React (TypeScript)
├─ packages/schema/           메타스키마: graph, target, workspace, events, node-schema, RPC 메시지
├─ packages/ui-sdk/           UI 확장 플러그인용 TS API (MIT)
├─ python/
│  ├─ kookabug_core/          그래프 로더·의미 검증, 러너, 판정, 이벤트 기록, 스냅샷, 권한 엔진, 입력 임대권, 감독자
│  ├─ kookabug_daemon/        워크스페이스 서비스 (UI·MCP가 붙는 곳)
│  ├─ kookabug_nodes/         코어 노드 (SDK로 작성)
│  ├─ kookabug_platform/      Windows 캡처·입력·창·DPI·OCR 백엔드
│  ├─ kookabug_mcp/           MCP 서버 (stdio shim)
│  ├─ kookabug_cli/           `kookabug` 명령
│  └─ kookabug_sdk/           노드 SDK (MIT, 별도 LICENSE)
├─ fixtures/sample-game/      예제 게임
├─ docs/                      사용자 문서
└─ LICENSE                    Apache-2.0
```

- **메타스키마**(`packages/schema`)는 파일과 통신 형식의 단일 출처다. 여기서 pydantic v2 모델과 TS 타입을 생성한다
- **노드 정의**는 메타스키마가 아니라 Python SDK 선언에서 생성한다 (`kookabug-sdk build`)
- 생성된 타입은 모양만 검사한다. 동적 출구, 링크 유효성, 호출 경로, 반복 범위 같은 **의미 검증은 Python 코어**가 최종 책임진다. 에디터는 코어의 검증 결과를 받아 표시한다
- 코어 노드도 `kookabug_sdk`로 작성한다

## 3. 프로세스와 통신

```
Electron UI ──WebSocket JSON-RPC──┐
                                  ├── kookabug daemon (워크스페이스당 1개)
에이전트 CLI ──stdio MCP── kookabug mcp ──┘      │ 인덱스, 검증, 실행 관리, events 구독·재전송
                                                 │ (= 감독자)
                                                 └─named pipe── runner (실행당 1개, Job Object)
                                                                 └─named pipe── plugin worker (실행에 귀속)
```

| 구간 | 방식 |
|---|---|
| UI ↔ daemon | 로컬 WebSocket(127.0.0.1) + JSON-RPC 2.0. 접속 정보는 `.kookabug/session.json` |
| 에이전트 ↔ MCP | 에이전트가 `kookabug mcp`(stdio)를 띄우고, 이것이 daemon에 붙는다 |
| daemon ↔ runner, runner ↔ worker | **named pipe** + 길이 접두 JSON-RPC. stdout·stderr는 프로토콜에 쓰지 않고 로그로만 받는다 (플러그인의 `print()`가 통신을 깨지 않게). 파이프는 byte mode·인스턴스 1·원격 거부, 같은 이름이 이미 있으면 만들기 실패(가로채기 방지). 프레임은 `uint32` little-endian 길이 + UTF-8 JSON(1바이트~16 MiB, 받는 쪽도 검사). 연결 직후 실행마다 무작위 키로 상호 HMAC-SHA256 도전·응답(양쪽이 서로를 확인). 모든 대기에 기한(accept·connect 30초, 인증 5초, 프레임 쓰기 10초 — 넘으면 그 연결은 실패), 읽기는 닫기가 끊는다. 보내기는 제한 있는 송신 큐에 넣고 바로 돌아온다(큐가 차면 연결을 잃은 것). 메시지 형식은 `packages/schema/rpc.schema.json`이고 양쪽 피어가 보내기 전·받은 뒤 같은 봉투 규칙으로 검사한다(틀린 요청은 오류로 답하고 처리하지 않음, 틀린 응답은 그 요청의 오류). 값은 표준 JSON 숫자(NaN·무한 금지, 정수 ±(2^53-1))와 중첩 128단까지이고, 받은 프레임이 이 규칙으로 읽히지 않으면 어느 요청의 응답인지 알 수 없으므로 `parse_error`를 보내고 그 연결을 실패로 한다 |
| 큰 데이터 | 캡처 픽셀은 runner의 **프레임 저장소**에만 두고 노드·워커에는 픽셀 없는 **참조 이미지**(`capture_id`·크기)를 넘긴다. 픽셀은 같은 프레임·같은 자르기면 한 번만 보관하고, 관측 호출이 쓰는 동안·열린 스텝의 최근 두 캡처(마지막 = 증거, 그 앞 = 연속 비교용)·출력 참조(최근 32개)로만 남긴다. 출력 참조는 바이트 예산(512 MiB)을 넘으면 오래된 것부터 버리고, 버린 프레임을 쓰면 `frame_expired`. 워커가 픽셀을 직접 읽는 공유 메모리는 M6 (M1은 runner가 `find`·`diff`·`ocr`을 대신한다). 파일은 기록용 artifacts만 |
| CLI 단독 | `kookabug run`은 daemon 없이 runner를 직접 띄우고 **CLI 프로세스가 감독자**다. 종료 코드 `0` 통과, `1` 실패, `2` 오류(취소·기한·runner 죽음·입력 임대권 거부 포함. 감독자가 기록 마무리에 실패하면 그래프 판정과 무관하게 `2`이고 판정은 그대로 보여 준다), `3` 건너뜀, `4` 실행 전 검증 오류, `5` 권한 거부·승인 필요, `6` 사용법·환경 오류. 기한은 `--deadline-ms` → `kookabug.json`의 `run.deadline_ms` → 30분. Ctrl+C 한 번은 취소, 두 번은 runner를 바로 끝낸다(어느 쪽이든 감독자가 기록을 마무리). `KOOKABUG_AGENT=<연결 ID>`를 붙이면 사람 없는 에이전트로 판정한다(CLI는 승인을 주지 않으므로 `ask`는 거부) |

### 계약

- **수명**: UI를 꺼도 daemon과 실행은 유지된다. daemon(감독자)이 죽으면 runner는 **감독자 프로세스 핸들로** 감지하고(통신 채널이 끊긴 것은 사망의 증거가 아니다 — 채널만 끊기면 runner는 기록만 남기고 계속하며, 판단은 살아 있는 감독자가 한다) 스스로 취소 절차를 밟는다. runner가 멈춰 그 절차를 끝내지 못하면 자기 종료 감시자가 `TerminateProcess(self)`로 끝낸다. 감독자와 runner가 둘 다 죽거나 멈춘 경우(이중 고장)는 그 자리에서 복구하지 않고, 다음 입력 임대권 획득자가 키를, 다음 기록 읽기가 "중단" 표시를 맡는다. daemon 재시작 후 실행을 이어받는 것은 MVP에서 하지 않는다
- **`session.json`**: PID, 시작 ID, 프로토콜 버전, 포트, 토큰. 이미 있는데 PID가 죽었거나 시작 ID가 다르면 오래된 파일로 보고 새로 만든다. 동시에 두 daemon이 만들려 하면 파일 잠금으로 하나만 이긴다
- **권한·입력 임대권·감독 코드는 `kookabug_core`에 하나만** 있고, daemon과 CLI가 같은 코드를 쓴다. 사람이 없는 실행에서 `ask`는 거부로 처리한다. 권한 판정 대상은 에이전트이고(사람의 직접 사용은 판정하지 않음), 정책은 사용자 설정·`.kookabug/local.json`·`kookabug.json`(팀 상한) 세 계층이다 ([[워크스페이스 구조]] "에이전트 권한"). 권한 설정 파일이 잘못되면 에이전트 요청은 전부 거부, `ask`는 승인 전에 실행하지 않는다. 판정은 공유 서비스(`WorkspaceService.authorize`) 하나가 한다
- **노드 실행과 통신 수신은 다른 스레드**다. 동기 노드가 돌고 있어도 취소·멈춤 요청을 받는다. 워커 ↔ runner는 양방향이다 (워커의 `ctx.capture()`가 runner로 요청을 보내는 동안에도 runner가 취소를 보낼 수 있다)
  - **입력은 runner의 입력 액터 하나만 보낸다**(단일 생산자). 노드의 `ctx.input.*`(코어 노드든 워커 요청이든)은 액터 큐에 요청을 넣고 완료를 기다리고, 취소를 받은 스레드는 액터에 신호만 준다. 액터는 키를 누르기 **전에** `input.down`을, 뗀 **뒤에** `input.up`을 기록하므로 프로세스가 어디서 죽어도 눌렸을 수 있는 키가 기록에서 빠지지 않는다. 기록 쓰기가 실패하면 액터는 그 뒤 입력을 막는다(대기 요청 취소, 눌린 키만 떼고 더 기록하지 않음) — 반쯤 쓴 줄 뒤에 이어 쓰면 읽기가 그 줄을 버려 실제로 누른 키가 빠지기 때문이다
- **기록 작성자는 runner 하나**다. 이벤트마다 `seq`를 붙여 `events.jsonl`에 쓰고, daemon은 파일을 구독해 UI에 다시 보낸다. UI가 느리거나 끊겨도 runner는 멈추지 않는다. UI는 다시 붙을 때 마지막 `seq` 이후를 요청한다. runner가 죽은 실행은 프로세스 종료를 확인한 뒤 **감독자만** 마무리 기록을 쓴다(runner 쪽에 복구 프로세스를 두지 않는다 — 한 실행에 감독자는 하나이므로 복구 작성자도 하나다)
- **프로세스 정리**: 실행마다 Windows Job Object를 만들어 우리가 띄운 runner·worker·보조 프로세스를 넣는다. `core.app.launch`로 띄운 게임은 넣되, `core.window.attach`로 붙은(사용자가 미리 띄운) 게임은 넣지 않는다. Job 종료가 키 해제를 대신하지는 않는다
  - Job 수명: 감독자가 이름 있는 Job(`Local\Kookabug.Run.<run_id>`)을 "마지막 핸들이 닫히면 안의 프로세스를 끝냄"(`KILL_ON_JOB_CLOSE`)으로 만들고, runner는 시작하자마자(어떤 자식도 띄우기 전에) 그 Job을 이름으로 열어 자기를 넣는다. 그래서 핸들이 둘이고, **둘 다 닫혀야** OS가 Job을 정리한다. 감독자만 죽으면 runner가 취소 순서를 밟고 끝나며 runner의 핸들이 마지막으로 닫혀 남은 워커가 끝난다. runner만 죽으면 감독자가 마무리한 뒤 Job을 끝낸다. 둘 다 죽으면 OS가 정리한다
  - Job 핸들은 상속하지 않고 다른 프로세스에 넘기지 않는다. runner 뒤에 띄운 워커는 생성 시점부터 Job 소속이라 "띄운 뒤 넣기" 사이의 경쟁이 없다
- **워커**: venv는 재사용하지만 워커 프로세스는 실행마다 새로 띄운다. 실행 중에는 플러그인 설치로 그 환경을 바꾸지 않는다
  - 실행 위치: 코어 노드(`core` 플러그인)는 runner 안에서, 그 밖의 플러그인 노드는 워커에서 실행한다. 워커 호스트는 SDK(`python -m kookabug_sdk.worker`)에 있어 플러그인 venv에 본체 의존성을 들이지 않는다. 캡처·OCR 격리는 별도 프로세스가 아니라 **관측 호출의 유효 기한**으로 한다: 캡처·찾기·OCR 호출 하나의 기한 = `min(설정 기한, 노드 기한 남은 시간, 전체 기한 남은 시간)`이고, 노드 기한이면 `ObservationTimeout`(노드의 `timeout` 출구), 설정 기한이면 `capture_timeout`, 전체 기한이면 `deadline_exceeded`. 기다리는 동안 50 ms마다 취소를 확인하고, 그래도 멈춘 관측은 M0b 하드 종료·복구 경로가 처리한다. 워커는 참조 이미지를 받고 픽셀 관측은 runner에 요청한다(위 "큰 데이터")
  - 시작 순서: 실행 스냅샷 → 워커를 띄워 `worker.hello` → 원격 노드 등록 → 그래프 의미 검증. runner는 플러그인 코드를 import하지 않고 hello로 받은 노드 스키마로 검증한다. hello가 기한(`run.worker_start_timeout_ms`, 기본 30초) 안에 오지 않거나 그 전에 워커가 죽으면 실행은 `error`(`worker_start_timeout`·`worker_died`)이고, 기다리는 동안에도 취소·전체 기한이 먹힌다
  - 입력·캡처·기록·변수·설정은 **runner가 한다**: 워커의 `ctx` 호출은 runner에 요청으로 오고, runner 주 스레드가 노드 응답을 기다리는 동안 그 요청을 처리한다. runner는 요청을 그 노드의 선언(`pure`·`effects`)으로 다시 검사하고, 노드 결과도 선언과 다시 대조한다 — 워커를 믿지 않는다. `ctx` 요청은 자기를 부른 노드 실행의 번호(`invoke`)를 싣고, runner는 지금 기다리는 실행의 번호가 아닌 요청(노드가 보관해 둔 이전 `ctx`, 남긴 스레드의 늦은 요청)을 처리하지 않는다 — 다음 노드의 선언·기록 정책으로 처리되면 안 된다
  - **입력은 공용 입력 서비스를 거친다** (M1): 워커의 `ctx.input.*` 요청도 코어 노드의 입력과 같이 그 스텝 ctx → 공용 입력 서비스(요청 창 고정, `match` 재검증·다시 찾기 — [[그래프 JSON 스키마 v0]] 6장) → 입력 액터 큐로 간다. 재검증 실패는 오류 종류 `stale_observation`으로 답하고 워커에서 같은 예외(`StaleObservation`)가 된다. 노드가 그것을 삼키고 끝내도 runner가 그 스텝을 처리되지 않은 fail로 본다
  - **관측 RPC의 기한**: 캡처·찾기·OCR·창 기다리기 요청은 노드 기한의 남은 시간(`deadline_ms`)을 싣고, runner는 위 유효 기한 규칙을 자기 시계로 다시 적용한다. 노드 기한으로 끝나면 오류 종류 `observation_timeout` → 워커의 `ObservationTimeout`(노드의 `timeout` 출구). 기한이 이미 지났으면 워커는 요청하지 않는다. runner 쪽 오류 코드(`frame_expired`·`window_gone`·`capture_timeout` 등)는 워커에서 `RunnerError(code)`이고, 노드가 잡지 않으면 runner는 **그 실행에서 자기가 낸 코드일 때만** 그 코드로 스텝을 끝낸다(아니면 `node_error`)
  - `ctx.path()`는 원본 워크스페이스가 아니라 **실행 스냅샷 루트**(`<실행 폴더>/snapshot`) 기준이다. 실행 내내 같은 파일을 읽는다
  - 값은 JSON으로 옮기고 SDK 타입은 `{"$kb": 태그}`로 표시한다. 비밀값은 경계 너머에서도 비밀값이다(원문은 인증된 파이프로만)
  - 실행 중 워커가 죽으면 그 스텝은 `error`(`worker_died`, 종료 코드)이고 다시 띄우지 않는다

### 취소 순서

1. 입력 차단 = 입력 액터의 게이트 닫기 (새 입력 요청 거부, 큐에서 기다리던 요청도 취소)
2. 키 해제 = 액터 큐 맨 앞에 release_all. 액터가 지금 하던 동작 하나를 끝내는 대로 이번 실행이 누른 키·마우스 버튼을 누른 차례의 거꾸로 뗀다. 취소를 받은 스레드는 입력 장치를 직접 부르지 않는다. 떼기는 입력 직전 확인(포그라운드·점 아래 창 등)을 거치지 않는다 — 게임이 포커스를 잃었어도 뗀다
3. 워커에 취소 요청 → 기한 안에 응답 없으면 워커 종료
4. 기록 확정 (`step.end` 중단 표시, 실행 결과)
5. runner 종료

runner가 이 순서를 못 밟고 죽으면 감독자가 2·4를 대신한다. 감독자도 없으면 다음 입력 임대권 획득자가 2를(입력하기 전에), 다음 기록 읽기가 4를(`run.end`·`step.end`가 없으면 "중단") 대신한다. 감독자가 키를 해제하려면 runner가 "지금 누르고 있는 키"를 이벤트로 남겨야 한다 (`input.down` / `input.up`).

감독자의 **복구 경로**는 runner가 어떻게 끝났든(정상·하드 종료·kill·크래시) 한 번 밟고, 다시 밟아도 결과가 같다: runner 종료를 프로세스 식별(PID + 생성 시각)로 확인 → 기록 끝의 잘린 줄 자르기 → 기록상 눌렸을 수 있는 키를 입력 임대권 안에서 해제(실행과 같은 입력 장치 — 실제 실행이면 SendInput, 누른 차례의 거꾸로, 확인 없이. 마우스 버튼은 그 순간 커서 자리에서 뗀다) → `run.end`가 없을 때만 `run.end`(`runner_died`) → `run.json`을 `run.end`에 맞춰 다시 만듦 → Job 정리. 종료를 확인하기 전에는 아무것도 쓰지 않는다. runner가 쓴 `run.end`는 덮어쓰지 않고, 열린 스텝에는 `step.end`를 쓰지 않는다("중단"). 감독자는 runner가 시작 인사(`runner.hello`)를 기한 안에 하지 못해도 runner를 끝내고 같은 경로로 마무리한다.

- **취소 사유**: `cancelled`(외부 취소) · `deadline_exceeded`(테스트 전체 기한) · `supervisor_lost`(감독자 사망). 먼저 정한 사유가 남고 `cancel.requested`·`run.end.cancel_reason`에 적는다. 기한 초과로 끝난 스텝은 `error`(`deadline_exceeded`), 나머지 취소는 `cancelled`
- **runner 안의 역할**: 노드는 주 스레드가 실행하고, 제어 스레드가 감독자 요청(취소·멈춤·재개)을 받는 즉시 답한다. 제어 스레드는 취소 순서를 시작만 한다(종료 단계 진입을 감시자에 알림 → 취소 토큰 → 액터 게이트 → 워커 취소 → 감독자에 `runner.stopping` → `cancel.requested`). 마무리(`run.end`·`run.json`·임대권 놓기)는 주 스레드 하나만 한다
- **기한 감시**: 제어 스레드가 runner 시작부터 잰 전체 기한에 취소 순서를 `deadline_exceeded`로 시작한다. 워커 노드도 취소 유예 뒤 끊긴다. 멈춘 시간은 M0b에서 기한에서 빼지 않는다(M3부터)
- **하드 종료**: 감독자는 취소를 보냈을 때, 또는 runner가 종료 단계에 들어갔다고 알렸을 때(`runner.stopping`: 기한 초과·감독자 사망 취소·정상 마무리 시작)부터 마무리 유예(`shutdown_grace_ms`, 기본 5초)가 지나도 runner가 살아 있으면 runner를 강제 종료하고 복구 경로를 밟는다. 제어 채널을 잃은 감독자도 곧바로 강제 종료한다(단 `runner.stopping`을 받은 뒤의 채널 끊김은 runner가 마무리 끝에 채널을 닫은 것일 수 있으므로 마무리 유예 타이머에 맡긴다)
- **자기 종료 감시자**: runner 안의 전용 스레드로, 잠금·기록·통신을 쓰지 않고 OS 대기와 `TerminateProcess(self)`만 한다. 감독자가 죽은 뒤 마무리 유예가 지나도, 또는 감독자가 살아 있는데 종료 단계 진입 뒤 마무리 유예 + 여유(10초)가 지나도 runner가 살아 있으면 끝낸다. 조건이 "마무리를 시작했는가"가 아니라 "프로세스가 아직 살아 있는가"라서, 주 스레드가 기록 잠금을 쥔 채 멈추거나 입력 장치 호출에서 멈춰도 끝난다

| 상황 | 끝내는 주체 | 키·기록 |
|---|---|---|
| 정상 종료, 취소·기한을 주 스레드가 유예 안에 마무리 | runner 주 스레드 | 주 스레드 (액터가 멈춘 뒤 임대권을 깨끗하게) |
| 취소·기한·정상 마무리 중 주 스레드·액터가 멈춤 | 감독자 하드 종료 (뒤 안전망: 자기 종료 감시자) | 감독자 복구 경로 |
| 제어 채널 끊김, 감독자 생존 | 감독자가 runner 강제 종료 | 감독자 복구 경로 |
| 감독자 사망, runner 정상 | runner 스스로 취소 → 정상 마무리 | runner 주 스레드 |
| 감독자 사망, runner 멈춤 / 둘 다 사망 (이중 고장) | 자기 종료 감시자 또는 OS (Job 마지막 핸들) | 그 자리에서 복구 없음: 키는 다음 임대권 획득자, 기록은 다음 읽기가 "중단" |
| runner kill·크래시 | — | 감독자 복구 경로 |

### 입력 임대권

- 하나의 Windows 사용자 세션에서 **입력을 보낼 수 있는 주체는 하나**다: 실행 / 녹화 / MCP 직접 제어 중 하나
- Windows 이름 있는 뮤텍스(`Local\Kookabug.InputLease`)로 구현한다. 소유 프로세스가 죽으면 OS가 풀어 준다. 소유자 정보(종류, 워크스페이스, 실행 ID·폴더, 프로세스 식별)와 "깨끗하게 놓았는가"(`clean`)는 옆 파일(`%LOCALAPPDATA%\Kookabug\input-lease.json`)에 적는다. 뮤텍스는 스레드 소유이므로 **전용 스레드**가 얻고 같은 스레드가 놓는다
- **얻을 때 앞 소유자 복구**: 얻은 직후 옆 파일을 보고 앞 소유자가 깨끗하게 놓지 않았으면, 입력하기 **전에** 앞 실행 기록에서 눌렸을 수 있는 키를 떼고 앞 실행 폴더에 복구 표시(`input-recovery.json`)를 남긴다. 표시가 이미 있으면 다시 떼지 않는다. 뮤텍스의 "버려짐(abandoned)"은 그때 다른 핸들이 열려 있어야만 보이므로 판단 근거로 쓰지 않는다
- **깨끗한 놓기는 입력 액터가 멈춘 뒤만**: 액터가 큐를 비우고 끝났고 눌린 키가 없을 때만 옆 파일을 `clean`으로 쓰고 놓는다. 그 밖의 종료(멈춘 액터, 하드 종료, kill)는 놓지 않은 채 끝나고 다음 획득자가 복구한다
- **감독자의 키 복구도 임대권 안에서만** 한다. runner가 죽은 뒤 감독자는 복구 표시가 있으면 건너뛰고, 없으면 임대권을 얻어(얻기 복구가 그 실행을 뗀다) 곧바로 깨끗하게 놓는다. 기한 안에 못 얻으면 지금 소유자가 이미 복구했어야 하므로 표시를 다시 본다. 그래서 감독자의 늦은 복구가 다음 실행의 입력을 건드리지 않는다
- **이중 고장**(감독자와 runner가 둘 다 죽거나 멈춤): 그 자리에서 키를 떼는 주체는 없다. 다음 임대권 획득자가 입력 전에 뗀다. 그때까지 키가 눌려 있을 수 있다
- 얻기 복구·감독자 복구의 떼기는 입력 직전 확인 없이 **그 실행의 입력 장치**로 한다(가짜 플랫폼은 같은 기록 파일, `windows`는 SendInput). 그래서 옆 파일의 소유자 정보에 입력 장치를 함께 적고, 다음 획득자는 자기 장치와 다르면 그 장치의 백엔드를 따로 만들어 뗀다(실제 실행이 남긴 키를 가짜 실행이 "뗐다"고 표시하거나, 가짜 키를 실제 장치로 떼지 않게). 떼기가 실패하면 복구 표시를 남기지 않는다(다음 획득자가 다시 뗀다)
- MVP는 이미 다른 주체가 갖고 있으면 **명시적으로 거부**하고 누가 갖고 있는지 알려 준다. 대기·양보는 이후 버전
- 디버거로 멈춘 실행도 임대권을 유지한다. 그동안 Agent가 직접 클릭하려면 실행을 끝내야 한다

### MCP

- 활성 툴셋은 **에이전트 연결별** 상태다
- `kb_graph_patch`는 기준 revision을 받는다. 그 사이 UI나 다른 연결이 고쳤으면 거부한다
- `kb_run_start`는 중복 방지 키를 받는다. 연결이 재시도해도 실행이 두 개 생기지 않는다

## 4. 배포

- Windows 설치 파일: electron-builder v26(NSIS) + electron-updater + GitHub Releases
- **M1(CLI만)**: Inno Setup 6 사용자별 설치 파일(관리자 권한 없음, `%LOCALAPPDATA%\Programs\Kookabug`, 사용자 `PATH`에 `bin`, 제거 등록). 폴더는 `python\`(PBS + 미리 설치한 wheel + 앱 로컬 VC++ 런타임) · `bin\kookabug.exe` · `ocr-models\` · `examples\sample-game\` · `licenses\` · `VERSION`. M2부터 NSIS로 바꾸고 폴더 구조는 유지한다 (`tools/installer/`)
  - **VC++ 런타임은 앱 로컬**: PBS에 `msvcp140.dll`이 없고 opencv·onnxruntime이 요구한다. 빌드 머신 Visual Studio의 `VC\Redist`에서 `msvcp140*`·`vcruntime140*`·`concrt140`을 `python.exe` 옆에 복사한다. 설치 트리의 모든 `.pyd`·`.dll`·`.exe` import를 Windows가 실제로 찾는 곳(그 파일 폴더·앱 폴더·System32)과 등록 근거가 확인된 DLL 폴더(패키지가 `os.add_dll_directory`로 더하는 `numpy.libs` 등, 그 패키지 안 파일에만)로만 풀어 보는 DLL 검사가 VC++ 런타임이 설치 폴더에서 풀리는지 확인한다. 설치 폴더 어딘가에 같은 이름이 있다는 것만으로는 통과시키지 않는다
  - **실행기**: uv가 만든 콘솔 실행기의 Python 경로 자원을 빌드 때 상대 경로(`..\python\python.exe`)로 바꾼다. 실행기는 상대 경로를 자기 폴더 기준으로 풀므로 설치 뒤 다시 만드는 단계가 없고 폴더를 옮겨도 돈다. 실행기 스텁에 정적으로 든 크레이트는 빌드에 쓰는 uv 판(고정, 빌드가 확인)의 `Cargo.lock`으로 만든 레포 SBOM과 원문으로 감사한다
  - **테스트 판**: 무인 설치 검사는 AppId·이름·기본 폴더·제거 등록 이름이 모두 다른 테스트 전용 판만 설치하고 HKCU 제거 등록이 끝에 처음과 같은지 본다. 개발자 PC의 실제 설치를 건드리지 않는다
  - **빼는 것**: `opencv-python`의 FFmpeg DLL(LGPL), PBS의 pip·`ensurepip`·`idlelib`. 파일과 그 `RECORD` 줄을 지우고 최종 트리 감사가 남은 것이 없는지 본다. 제거 목록은 감사 표(`[[strip]]`) 하나다
  - 설치 폴더 + 가장 긴 상대 경로가 260자(MAX_PATH)를 넘으면 설치 파일이 복사 전에 멈춘다 (onnxruntime 안 경로가 약 150자)
- Python 런타임은 **앱에 포함**한다 (python-build-standalone + 코어 의존성 미리 설치). 플러그인 의존성 설치용 uv도 포함한다 — M1 설치본에는 넣지 않는다(플러그인 설치가 생길 때, `uv.exe`에 정적으로 들어간 크레이트들의 라이선스 원문과 함께)
- CLI만 쓰는 CI용으로 PyPI 배포 (`pip install kookabug`)
- **라이선스 감사는 M0부터 CI**에서 한다: Python 의존성(pip-licenses), JS 의존성, python-build-standalone 배포물에 들어 있는 라이선스 메타데이터, OCR 모델·사전 파일. 결과를 설치 파일의 `THIRD_PARTY_NOTICES`로 묶는다
  - **네이티브 파일도 구성요소별로** 본다: wheel·Python 배포본 안의 DLL·pyd·exe는 전부 `tools/native-licenses.toml`의 항목(파일 glob → 그 파일에 정적으로 들어간 구성요소 전부의 SPDX 식·이유)에 맞아야 하고, 식의 모든 부분이 허용이어야 한다. **식의 모든 구성요소에 라이선스 원문이 연결돼야 한다**: 배포물 안 파일이나 레포 `tools/third_party_licenses/`의 원문, 원문마다 반드시 있어야 하는 글귀로 확인하고 NOTICES에 그대로 싣는다. Rust 확장은 동봉 SBOM의 크레이트마다 원문 절이 있어야 한다(`tools/fetch_crate_licenses.py`가 crates.io에서 모은다). SPDX 밖 배포 조건(VC++ 재배포 파일·Inno Setup·sqlite blessing·Intel IPP)은 원문 위치와 처리 근거를 적은 `LicenseRef-*`로 그 표에서만 허용한다. 조건부 라이선스(MPL-2.0)가 DLL 안 구성요소이면 그 네이티브 항목의 이유를 예외 근거로 삼는다
  - **두 단계**: 빌드 입력 감사(감사 venv·설치 전 트리 — 금지 라이선스 파일·표에 없는 파일은 제거 목록에 있을 때만 허용, 제거 glob이 아무것도 못 맞히면 실패)와 최종 설치 트리 감사(제거 목록과 무관하게 금지 파일이 남으면 실패, 모든 네이티브 파일이 표에 맞아야 함, `dist-info/RECORD`와 실제 파일이 서로 맞아야 함, 설치본 `ocr-models/` 안의 모델·라이선스 근거 원문 해시, 근거 원문은 NOTICES에 실음). 설치 파일 빌드는 설치 전 스테이징 트리에, CI는 무인 설치 결과에도 최종 트리 감사를 건다. 설치 프로그램이 설치 때 더하는 파일(Inno 제거 프로그램)은 스테이징 감사에서도 있는 것으로 보고 NOTICES에 싣는다. 설치본 NOTICES의 Python 패키지 절은 스테이징 Python을 스캔해 만든다(설치된 집합 = 감사 기준 집합 + Kookabug 패키지). 어느 쪽이든 읽을 수 없는 폴더는 실패다(그 안을 판정하지 못했으므로). 모델 표의 경로는 모델 폴더 안 상대 경로만 받는다
  - **numpy 한정 예외**: numpy의 OpenBLAS DLL에 정적으로 들어간 GCC 런타임(`GPL-3.0-or-later WITH GCC-exception-3.1`)은 numpy 패키지에서만 허용한다(GCC Runtime Library Exception). 거부 패턴보다 먼저 보되 다른 패키지에서 같은 식이 나오면 금지 그대로다. NOTICES에 예외와 이유를 적는다
- 코드 서명: SignPath(오픈소스용) 신청. 자동 승인되지 않고, 남이 만든 바이너리(Python, uv)를 재서명하는 데 제약이 있으므로 서명 범위를 신청 때 확인한다. 서명 전까지는 SmartScreen 경고를 문서로 안내한다
- M1 완료 기준에 "Python 없는 깨끗한 Windows에서 설치·실행"이 들어 있다. 배포는 마지막에 붙이는 일이 아니다

## 5. 캡처·입력·비전

| 영역 | 결정 |
|---|---|
| 캡처 | **WGC**(창 단위)를 먼저 완성한다. DXGI는 검증된 뒤 **명시적으로 고르는** 선택 경로로 추가한다. 검은 프레임만 보고 백엔드를 자동으로 바꾸지 않는다 (검은 로딩 화면은 정상일 수 있고, DXGI는 모니터 단위라 위에 겹친 다른 창을 찍는다). 백엔드 선택은 사전 기능 검사와 명시적 API 오류로만. PrintWindow·BitBlt 자동 폴백은 이후 버전. **WGC는 화면이 바뀔 때만 프레임을 준다**: 창 바인딩마다 세션 하나가 최신 프레임을 들고 있고, 캡처 요청은 50 ms 동안 새 프레임을 기다린 뒤 오지 않으면 최신 프레임을 이 관측으로 **재사용**한다(세션이 살아 있고, 첫 프레임을 받았고, 바인딩이 살아 있고 최소화 아니고, 지금 창 크기·DPI가 그 프레임과 같을 때) — 멈춘 화면은 오류가 아니다. 장애 구분: 첫 프레임이 기한 안에 안 옴 → `capture_timeout`, 크기·DPI가 바뀌었는데 맞는 프레임이 안 옴 → `capture_timeout`(0.25초 안에 안 오면 세션을 한 번 다시 열어 첫 프레임을 받는다 — windows-capture는 크기가 바뀐 프레임을 버리므로 멈춘 화면은 새 크기 프레임을 주지 않는다), 세션 종료·콜백 예외 → 한 번 다시 만들고 그래도 안 되면 `capture_failed`, 창 닫힘 → `window_gone`, 최소화 → `window_minimized`, 세션 생성 실패 → `capture_unsupported`. 0.25초는 그 세션이 불일치를 처음 본 때부터 재므로 짧은 노드 기한의 요청이 이어져도 다시 열기가 진행되고, 다시 연 세션의 첫 프레임 대기도 다음 요청이 이어받는다. 설정 기한 안에 프레임을 못 준 세션은 버린다(노드 기한이면 둔다). 세션 시작처럼 끊을 수 없는 호출 뒤와 결과 확정 직전에 취소·기한을 다시 보아, 기한 뒤에 준비된 프레임을 성공으로 내보내지 않는다. 창이 닫히면(`on_closed`·파괴 이벤트) 그 세션의 픽셀을 다시 캡처하지 않아도 바로 놓고, 네이티브 세션은 다음 캡처·`close`·실행 끝 회수에서 실제로 멈춘다(`close`는 멈추고 끝나기까지 확인해야 성공). 사망 알림은 콜백·추적기 스레드에서 오므로 서비스 잠금을 기다리지 않고 큐로 넘기며, 서비스 잠금 안에서는 상태만 바꾸고 네이티브 세션 멈추기(콜백 스레드 join)는 잠금 밖에서만 한다 — 시작 중 종료·회수 중 종료가 서로 기다리지 않게. 프레임은 확장 프레임 경계 크기이므로 클라이언트 영역만 잘라 쓴다(커서·테두리 끔). 자른 픽셀은 자기 메모리를 가진 복사본이다 — 뷰는 전체 프레임 할당을 붙잡아 저장소 예산을 속인다. 장시간 검사(`soak`, 로컬 필수): 세션 200회·크기 변경 500회·캡처 10,000회에서 핸들 증가 ≤ 50, 스레드 ≤ 2, 개인 바이트 ≤ 64 MiB, 모든 세션 종료 — WGC 세션을 열 때마다 남는 `ALPC Port` 핸들(windows-capture·WGC 쪽, 세션당 최대 하나)은 따로 센다 |
| 프레임 정보 | 프레임마다 백엔드, 대상 창(바인딩), 클라이언트 크기·화면 원점, DPI, 캡처 영역, 프레임 번호, 재사용 여부와 **시각 두 개**를 붙인다: `observed_at`(이 요청이 관측으로 확정된 시각 — 판정·기록이 "이 시점의 화면"으로 쓰는 값)과 `pixels_at`(그 픽셀이 WGC에서 온 시각). 프레임 번호는 프로세스 안에서 유일해 다른 창·다시 만든 세션의 프레임과 섞이지 않는다. 백엔드가 바뀌면 기존 관측값은 무효 |
| 입력 | SendInput. 입력 직전(누르기·글자·이동·휠마다, **떼기·전부 떼기·복구에는 하지 않음** — 떼기까지 막으면 복구가 막힌다) 창 유효성·최소화·포그라운드·점 아래 창·권한 수준·입력 데스크톱 확인. **포그라운드**(키보드·글자) = 포그라운드 창이 대상 창 자신이거나 대상 창이 (소유자 사슬로) 소유한 팝업. 같은 프로세스의 독립 최상위 창은 거부(`window_not_foreground`). **점 아래 창**(마우스) = 클릭 화면 점의 창을 부모 사슬(`GA_ROOT`)로 올린 최상위 창이 정확히 대상 창. 대상 창의 소유 팝업이 덮은 지점도 거부(`point_obscured`) — WGC 창 캡처에는 소유 팝업이 찍히지 않아 관측과 입력 대상이 어긋난다. 팝업을 누르려면 그 팝업을 대상 창으로 붙인다. 게임 무결성 수준이 runner보다 높으면(토큰을 읽을 수 없는 경우 포함) `target_elevated` — UIPI가 입력을 조용히 버리므로 관리자 권한 터미널에서 실행하라고 안내 (자동 권한 상승 없음). 잠금 화면·UAC 화면이면 `input_desktop_unavailable` |
| 창 | 창 찾기는 제목(대소문자 무시 부분 일치, `/정규식/`)·실행 파일 이름·PID, 보이는 최상위·소유자 없는 창(소유 팝업은 명시적으로)·`cloaked` 제외, Z 순서 앞. 띄운 게임의 창은 실행 Job 안 모든 프로세스에서 찾는다(런처형). **창 수명 추적**: runner가 창을 정할 때 바인딩(hwnd·PID·프로세스 생성 시각·실행 안 ID)을 만들고, 창 파괴 이벤트(`EVENT_OBJECT_DESTROY`)나 WGC 세션 종료가 오면 그 바인딩은 죽는다 — 같은 프로세스가 같은 hwnd 값으로 새 창을 만들어도 옛 참조는 `window_gone`. 파괴 이벤트는 비동기라, 파괴와 이벤트 도착 사이 수 ms 안의 같은 hwnd 재사용은 막지 못할 수 있다(문서화된 한계). 지원하지 않는 조건은 정해진 오류 코드로 끝난다(`window_gone`·`window_minimized`·`window_not_foreground`·`point_obscured`·`window_mismatch`·`target_elevated`·`input_desktop_unavailable`·`dpi_awareness_unavailable`·`launch_failed` 등, 메시지에 대상 창·지금 앞에 있는 창) |
| DPI | runner 진입점 첫 줄에서 프로세스를 Per-Monitor V2로 정하고 확인(이미 다른 수준이면 `dpi_awareness_unavailable`). 캡처·입력 좌표의 단일 기준은 **대상 창 클라이언트 영역 물리 픽셀**: 정규화 사각형은 그 순간 클라이언트 크기를 곱하고(네 변 각각 반올림), 화면 좌표는 입력 직전에만 만든다. 창 함수는 좌표를 읽는 동안 그 스레드만 PMv2로 두어 프로세스 수준과 무관하게 물리 픽셀을 본다. 감독자는 좌표를 쓰지 않으므로(복구의 떼기만) 프로세스 수준을 바꾸지 않는다 |

| OCR | 엔진 교체 가능(`kookabug.json` `ocr.engine`, M1 값 `rapidocr` 하나). **기본 RapidOCR**(ONNX Runtime CPU): RapidOCR 3.10의 검출(DB)·인식(CTC) 전후처리를 옮기고 방향 분류는 하지 않는다. **검출 크기 정책**(`DetConfig`, `kookabug.json` `ocr.det`로 바꿀 수 있음): 검출 모델은 입력 픽셀이 많으면 작은 글자를 놓친다(실측: 작은 글자 하나가 1024×640까지는 거의 다 잡히고 1024×1024·1920×1080에서는 거의 못 잡힘, 줄여 넣으면 더 놓침). 그래서 1024×640 픽셀까지는 한 번에, 넘으면 원래 해상도로 640 정사각 타일(겹침 128)마다 검출하고, 타일 경계에서 잘린 상자·겹친 곳의 같은 상자를 합친다. 겹침보다 큰 글자는 전체를 1024×640 픽셀로 줄여 한 번 더 검출해 잡는다. 검출 입력은 짧은 변이 64보다 작을 때만 늘리고(RapidOCR 기본 736은 작은 영역을 열 배 넘게 키워 1초 넘게 걸리고 글자가 깨짐 — PaddleOCR 3.x 검출 기본값), 긴 변 4096이 넘을 때만 줄인다(4K는 그대로). 낮고 긴 한 줄 영역의 세로 여백은 타일마다 붙인다. 화면 전체 읽기는 느리다(측정: 1024×640 약 0.4~0.7초, 1920×1080 약 1.5초, 3840×2160 약 4~5초) — 노드는 영역을 주는 것이 기본이다. 관측 한 번의 유효 기한에 설정 기한(`run.capture_timeout_ms`, 기본 2000)이 들어가므로, 큰 화면 전체를 읽는 그래프는 그 설정을 읽기 시간보다 크게 잡아야 한다(노드 timeout만 늘려서는 설정 기한을 넘지 못하고 `capture_timeout`, 엔진은 기한을 늘리지 않는다). 모델은 검출 `PP-OCRv6_det_small`·인식 `korean_PP-OCRv5_rec_mobile`(사전은 ONNX 메타데이터) 두 개를 `ocr/models.toml`에 주소·SHA256·크기·라이선스·근거 원문(PaddleOCR `LICENSE`, RapidOCR `MODEL_LICENSES.md`)으로 고정하고, git에 넣지 않고 `tools/fetch_ocr_models.py`가 받아 확인한다(CI는 캐시). 찾는 순서는 `KOOKABUG_OCR_MODELS`(주면 그 폴더만) → 설치본 `ocr-models/` → 레포 `build/ocr-models/`, 없으면 `ocr_model_missing`, 해시가 다르면 `ocr_model_corrupt`. **실행 중에 내려받지 않는다**. 추론 한 번은 끊을 수 없어 시작 전·추론마다 직전과 끝난 바로 뒤(결과를 후처리에 넘기기 전)에, 그리고 검출 후처리 윤곽 16개마다·타일 상자 합치기(이웃만 비교, 상자 1200개 약 20 ms) 비교 256번·판정 64번마다·상자 자르기마다 취소·기한을 보고 넘었으면 결과를 버린다 — 노드 timeout은 최대 추론 한 번만큼 늦는다(측정: 타일 검출 한 번 약 0.1초, 한 번에 검출하는 1024×640 약 0.3~0.4초, 인식 묶음 한 번 0.4초 이하). **Windows OCR은 선택 백엔드**: Microsoft가 데스크톱에서 패키지 ID를 요구하므로, 지원 조건을 확인한 환경에서만 켠다. Tesseract는 넣지 않는다. 한국어 모델의 정확도·속도는 M1에서 예제 게임(`fixtures/sample-game/ocr-samples`)과 실제 게임 폰트로 `tools/ocr_bench.py`가 측정한다 |

- **Agent 판단 노드**(`cli_judge`, `api_judge`)가 부르는 에이전트에는 Kookabug 제어 도구를 주지 않는다. 이미지와 질문만 준다. 에이전트 패널의 Agent와 실행 환경을 분리한다
