## 1. 마일스톤

- **예제 게임**: 레포 안에 작은 가짜 게임(`fixtures/sample-game`)을 둔다. 타이틀 → (점검 팝업) → 로그인 → 로비 → 월드 → 인벤토리. 실행 옵션으로 점검·로그인 실패·느린 로딩·해상도를 바꾼다. CI E2E와 문서 예시가 모두 이 게임을 쓴다. 헤드리스 CI용으로 화면 PNG와 장면 전이 표(`frames/scenario.json`, 게임 코드에서 생성)를 함께 둔다

## 2. 레포 구조

```
kookabug/
├─ apps/desktop/              Electron + React (TypeScript)
├─ packages/schema/           메타스키마: graph, target, workspace, events, node-schema, RPC 메시지(내부 rpc, UI ↔ daemon daemon-rpc), session, JS 전송 코덱(wire)
├─ packages/ui-sdk/           UI 확장 플러그인용 TS API (MIT)
├─ python/
│  ├─ kookabug_core/          그래프 로더·의미 검증, 러너, 판정, 이벤트 기록, 스냅샷, 권한 엔진, 입력 임대권, 감독자
│  ├─ kookabug_daemon/        워크스페이스 서비스 (UI·MCP가 붙는 곳)
│  ├─ kookabug_nodes/         코어 노드 (SDK로 작성)
│  ├─ kookabug_platform/      Windows 캡처·입력·창·DPI·OCR 백엔드
│  ├─ kookabug_mcp/           MCP 서버 (stdio shim)
│  ├─ kookabug_cli/           `kookabug` 명령
│  └─ kookabug_sdk/           노드 SDK (MIT, 별도 LICENSE)
├─ fixtures/sample-game/      예제 게임
├─ docs/                      사용자 문서
└─ LICENSE                    Apache-2.0
```

- **메타스키마**(`packages/schema`)는 파일과 통신 형식의 단일 출처다. 여기서 pydantic v2 모델과 TS 타입을 생성한다. daemon-rpc는 메서드 표(params·result·권한 도구·렌더러 표면)도 담고, JS 쪽 런타임 검사(`src/rpcCheck.ts`)가 같은 스키마를 읽는다. JS 값을 daemon으로 보내는 직렬화는 전송 코덱 `src/wire.ts` 하나다
- **노드 정의**는 메타스키마가 아니라 Python SDK 선언에서 생성한다 (`kookabug-sdk build`)
- 생성된 타입은 모양만 검사한다. 동적 출구, 링크 유효성, 호출 경로, 반복 범위 같은 **의미 검증은 Python 코어**가 최종 책임진다. 에디터는 코어의 검증 결과를 받아 표시한다
- 코어 노드도 `kookabug_sdk`로 작성한다

## 3. 프로세스와 통신

```
Electron UI ──WebSocket JSON-RPC──┐
                                  ├── kookabug daemon (워크스페이스당 1개)
에이전트 CLI ──stdio MCP── kookabug mcp ──┘      │ 인덱스, 검증, 실행 관리, events 구독·재전송
                                                 │ (= 감독자)
                                                 └─named pipe── runner (실행당 1개, Job Object)
                                                                 └─named pipe── plugin worker (실행에 귀속)
```

| 구간 | 방식 |
|---|---|
| UI ↔ daemon | 로컬 WebSocket(127.0.0.1) + JSON-RPC 2.0. 접속 정보는 `.kookabug/session.json`(형식 `session.schema.json`). 텍스트 프레임 하나에 메시지 하나(최대 16 MiB, 바이너리 프레임이면 닫음), 값 규칙은 named pipe와 같다. 업그레이드 요청의 `Host`가 `127.0.0.1:<포트>`가 아니거나 `Origin`이 있으면 거부하고, 첫 메시지는 5초 안의 `session.hello {token, protocol, client}`(토큰 상수 시간 비교)다. 연결 하나에 주체 하나(`ui` → 판정 없는 사용자, `agent` → 그 에이전트). 메서드·알림·오류는 `daemon-rpc.schema.json`이 단일 출처이고, 오류는 표준 코드에 `-32100 request_failed` 하나를 더해 종류를 `error.data.code`(snake_case)에 넣는다. 정지 화면·미리보기 같은 이미지는 RPC에 싣지 않고 `.kookabug/cache/editor/`에 쓴 뒤 이름만 보낸다(주 프로세스의 `kbimg://`가 서비스). 실행 기록의 증거·썸네일·영상도 RPC에 싣지 않고 실행 폴더 기준 경로만 보낸다(`kbimg://ws/runs/<실행 폴더>/…`). 영상(`.mp4`)은 실행 폴더의 `video/` 바로 안 파일만 받고, `Range` 요청에는 파일 범위 206 응답을 준다(영상 탐색). CSP에 `media-src kbimg:` (M3). **JS 쪽 직렬화는 전송 코덱 `wireStringify`만 쓴다**: 비유한 수는 보내지 않고 오류를 내며, 안전 범위 밖 정수값인 수(원래 Python float인 `1e20` 등)는 지수 표기로 보내 Python에서 float로 돌아오게 한다 |
| 에이전트 ↔ MCP | 에이전트가 `kookabug mcp`(stdio)를 띄우고, 이것이 daemon에 붙는다 |
| daemon ↔ runner, runner ↔ worker | **named pipe** + 길이 접두 JSON-RPC. stdout·stderr는 프로토콜에 쓰지 않고 로그로만 받는다 (플러그인의 `print()`가 통신을 깨지 않게). 파이프는 byte mode·인스턴스 1·원격 거부, 같은 이름이 이미 있으면 만들기 실패(가로채기 방지). 프레임은 `uint32` little-endian 길이 + UTF-8 JSON(1바이트~16 MiB, 받는 쪽도 검사). 연결 직후 실행마다 무작위 키로 상호 HMAC-SHA256 도전·응답(양쪽이 서로를 확인). 모든 대기에 기한(accept·connect 30초, 인증 5초, 프레임 쓰기 10초 — 넘으면 그 연결은 실패), 읽기는 닫기가 끊는다. 보내기는 제한 있는 송신 큐에 넣고 바로 돌아온다(큐가 차면 연결을 잃은 것). 메시지 형식은 `packages/schema/rpc.schema.json`이고 양쪽 피어가 보내기 전·받은 뒤 같은 봉투 규칙으로 검사한다(틀린 요청은 오류로 답하고 처리하지 않음, 틀린 응답은 그 요청의 오류). 값은 표준 JSON 숫자(NaN·무한 금지, 정수 ±(2^53-1))와 중첩 128단까지이고, 받은 프레임이 이 규칙으로 읽히지 않으면 어느 요청의 응답인지 알 수 없으므로 `parse_error`를 보내고 그 연결을 실패로 한다 |
| daemon ↔ 녹화 훅 프로세스 (M4) | 녹화 중에만 사는 자식 프로세스 하나가 저수준 마우스·키보드 훅(`WH_MOUSE_LL`·`WH_KEYBOARD_LL`)을 건다. daemon(asyncio·매칭·OCR)이나 캡처 콜백과 같은 프로세스에 두지 않는다 — 훅 함수가 늦으면 시스템 전체 입력이 늦고 Windows가 알리지 않고 훅을 뗀다. 통신은 runner와 같은 named pipe + 길이 접두 JSON + 상호 HMAC, 응답 없는 JSON-RPC 알림만(`hook.hello`·`hook.events`·`hook.obs`·`hook.ime`·`hook.health` ↑, `hook.stop` ↓, 형식 `recorder-hook.schema.json`). 시각은 daemon이 띄울 때 준 녹화 기준 시각부터 잰 단조 시계 ns(값 규칙 ±(2^53-1) 안, 캡처 프레임 도착 시각과 같은 시계). 훅 프로세스는 daemon을 Job(`KILL_ON_JOB_CLOSE`)과 부모 프로세스 핸들 대기로 따른다 — daemon이 죽으면 함께 끝나고 OS가 훅을 뗀다. 녹화하지 않는 동안 시스템에 우리 훅은 없다. **훅 콜백**은 단조 시각·`event_id`·구조체 필드 복사·우리 표식이면 버리기·이동은 칸 하나 덮어쓰기(합치기)·중요 이벤트(버튼·휠·키)는 그 직전 이동을 먼저 넣고 `crit_seq`를 매겨 고정 4096칸 큐에 넣기(차 있으면 기다리지 않고 버리고 `overflow`)·`CallNextHookEx`뿐이다 — 창 조회·메시지·잠금 대기·I/O 없음. 나머지는 다른 스레드다: **관측 스레드**(중요 이벤트마다 즉시 관측 하나, 메시지 없는 API와 창 이벤트로 무효화하는 Z 순서 표), **IME 표본 스레드**(대상에 묻는 유일한 조회 `SendMessageTimeoutW` 50 ms — 관측과 따로 돌아 조회가 막혀도 관측이 밀리지 않음, 실패도 조회 구간을 실어 받는 쪽이 겹치는 키를 판정 불가로), **송신 스레드**(묶음·관측·표본·500 ms 생존 보고, 파이프 쓰기가 막히면 기다리고 그동안 큐가 차면 `overflow`). daemon은 `batch_no`·`crit_seq` 빈틈·`overflow`를 실제 유실로 보고 그 번호에서 잘라 `input_overflow`로 멈추고(그 앞 동작은 남김 — 훅은 첫 버린 이벤트 앞의 큐를 다 보낸 묶음부터 넘침을 알리고, daemon은 그 묶음 안 유실 앞 이벤트도 넘긴 뒤 훅을 정상으로 멈춰 그 이벤트들의 관측·IME 표본을 파이프 EOF까지 받고 나서 멈춤을 알린다), 생존 감시 셋(프로세스 끝·파이프 EOF / 생존 보고 2초 없음 / `GetLastInputInfo`가 앞섰는데 1초 넘게 훅 이벤트 없음 — OS가 훅을 뗀 경우) 중 하나면 `hook_lost`로 멈춘다. 다른 프로그램이 합성한 입력(`injected`)은 녹화하지 않고 센다. 정상 멈춤은 `hook.stop` → 훅 해제·마지막 송신 → 파이프 EOF가 완료 경계이고, daemon은 EOF까지 받은 메시지를 모두 넘긴 뒤 멈춤을 끝낸다(넘기기가 기한을 넘기면 정상 완료와 구별되는 미완료로 알리고 그 뒤 콜백은 없다). 정지 사유와 멈춤 알림은 한 잠금 아래 상태 기계 하나가 정하고(읽기·감시·정지 요청은 사건만 알린다), 넘침 마무리 상태는 소비자 콜백 전에 정한다. 녹화 중 훅 프로세스가 끝나면 받은 메시지를 EOF까지 읽은 뒤 판정하고(그 안에 넘침이 있으면 넘침), 생존 감시는 읽기 스레드가 받은 큐를 다 비운 순간에만 후보를 계산해 알린다(후보 계산은 스트림 상태를 바꾸지 않는다 — 소비자 콜백이 늦어 쌓인 생존 보고를 처리한 뒤 다시 잰다). 우리 표식만 버린 경우에도 훅은 빈 묶음으로 누적 개수(`dropped_marker`)를 알린다 — 멈춤 알림은 언제나 유실 앞 이벤트·관측·표본 뒤다 |
| 큰 데이터 | 캡처 픽셀은 runner의 **프레임 저장소**에만 두고 노드·워커에는 픽셀 없는 **참조 이미지**(`capture_id`·크기)를 넘긴다. 픽셀은 같은 프레임·같은 자르기면 한 번만 보관하고, 관측 호출이 쓰는 동안·열린 스텝의 최근 두 캡처(마지막 = 증거, 그 앞 = 연속 비교용)·출력 참조(최근 32개)로만 남긴다. 출력 참조는 바이트 예산(512 MiB)을 넘으면 오래된 것부터 버리고, 버린 프레임을 쓰면 `frame_expired`. 워커가 픽셀을 직접 읽는 공유 메모리는 M6 (M1은 runner가 `find`·`diff`·`ocr`을 대신한다). 파일은 기록용 artifacts만 |
| CLI 단독 | `kookabug run`은 daemon 없이 runner를 직접 띄우고 **CLI 프로세스가 감독자**다. 종료 코드 `0` 통과, `1` 실패, `2` 오류(취소·기한·runner 죽음·입력 임대권 거부 포함. 감독자가 기록 마무리에 실패하면 그래프 판정과 무관하게 `2`이고 판정은 그대로 보여 준다), `3` 건너뜀, `4` 실행 전 검증 오류, `5` 권한 거부·승인 필요, `6` 사용법·환경 오류. 기한은 `--deadline-ms` → `kookabug.json`의 `run.deadline_ms` → 30분. Ctrl+C 한 번은 취소, 두 번은 runner를 바로 끝낸다(어느 쪽이든 감독자가 기록을 마무리). `KOOKABUG_AGENT=<연결 ID>`를 붙이면 사람 없는 에이전트로 판정한다(CLI는 승인을 주지 않으므로 `ask`는 거부) |

### 계약

- **수명**: UI를 꺼도 daemon과 실행은 유지된다. daemon(감독자)이 죽으면 runner는 **감독자 프로세스 핸들로** 감지하고(통신 채널이 끊긴 것은 사망의 증거가 아니다 — 채널만 끊기면 runner는 기록만 남기고 계속하며, 판단은 살아 있는 감독자가 한다) 스스로 취소 절차를 밟는다. runner가 멈춰 그 절차를 끝내지 못하면 자기 종료 감시자가 `TerminateProcess(self)`로 끝낸다. 감독자와 runner가 둘 다 죽거나 멈춘 경우(이중 고장)는 그 자리에서 복구하지 않고, 다음 입력 임대권 획득자가 키를, 다음 기록 읽기가 "중단" 표시를 맡는다. daemon 재시작 후 실행을 이어받는 것은 MVP에서 하지 않는다
- **`session.json`**: PID, 프로세스 생성 시각, 시작 ID, 프로토콜 버전, daemon 판, 포트, 토큰, 워크스페이스, 시작 시각(형식 `session.schema.json`)
  - **잠금이 판단 근거다**: daemon은 `.kookabug/daemon.lock`을 공유 없이(상속되지 않는 핸들로) 열어 살아 있는 동안 쥔다. 프로세스가 죽으면 OS가 풀어 준다. 잠금을 얻은 뒤 포트를 열고 `session.json`을 같은 폴더 임시 파일 + replace로 쓰고, 끝날 때 자기 시작 ID인 경우에만 지운다. 잠금을 얻은 daemon에게 남아 있는 `session.json`(죽은 PID·다른 생성 시각·손상된 파일)은 오래된 파일이다
  - **경쟁에서 진 쪽**: 잠금 충돌이면 곧바로 파일을 읽지 않고 15초 안에 **유효한 세션**(형식이 맞고, PID·생성 시각이 살아 있고, 그 포트로 `session.hello` 인증이 성공함)이 나올 때까지 다시 읽는다. 나오면 "이미 실행 중"으로 종료 코드 0, 기한을 넘기면 6이다. 잠금 파일 접근 거부·I/O 오류는 경쟁이 아니라 곧바로 6이다. 클라이언트도 같은 유효성으로 붙고, 같은 시작 ID에 다시 붙는 것(일시적인 연결 실패)도 정상이다
  - **끝나는 때**: 연결도 진행 중인 실행도 없는 상태가 유휴 시간(기본 600초, `--idle-timeout-s`) 이어지면 스스로 끝난다. `daemon.shutdown`은 진행 중인 실행이 있으면 `run_active`로 거부하고, `force`면 실행을 취소하고 마무리를 기다린 뒤 끝낸다. agent 연결은 `daemon.shutdown`을 쓸 수 없다. 로그는 `.kookabug/logs/daemon-<시각>-<PID>.log`(최근 20개)다
  - **판이 다를 때**: `session.hello`의 프로토콜 판이 다르면 `protocol_mismatch`를 답하고 연결을 닫지 않는다. 그 연결은 `daemon.shutdown`만 받는다(앱의 "daemon 다시 시작"). 토큰이 틀리면 판과 무관하게 `unauthenticated`로 닫는다
- **권한·입력 임대권·감독 코드는 `kookabug_core`에 하나만** 있고, daemon과 CLI가 같은 코드를 쓴다. 사람이 없는 실행에서 `ask`는 거부로 처리한다. 권한 판정 대상은 에이전트이고(사람의 직접 사용은 판정하지 않음), 정책은 사용자 설정·`.kookabug/local.json`·`kookabug.json`(팀 상한) 세 계층이다 ([[워크스페이스 구조]] "에이전트 권한"). 권한 설정 파일이 잘못되면 에이전트 요청은 전부 거부, `ask`는 승인 전에 실행하지 않는다. 판정은 공유 서비스(`WorkspaceService.authorize`) 하나가 한다
- **노드 실행과 통신 수신은 다른 스레드**다. 동기 노드가 돌고 있어도 취소·멈춤 요청을 받는다. 워커 ↔ runner는 양방향이다 (워커의 `ctx.capture()`가 runner로 요청을 보내는 동안에도 runner가 취소를 보낼 수 있다)
  - **입력은 runner의 입력 액터 하나만 보낸다**(단일 생산자). 노드의 `ctx.input.*`(코어 노드든 워커 요청이든)은 액터 큐에 요청을 넣고 완료를 기다리고, 취소를 받은 스레드는 액터에 신호만 준다. 액터는 키를 누르기 **전에** `input.down`을, 뗀 **뒤에** `input.up`을 기록하므로 프로세스가 어디서 죽어도 눌렸을 수 있는 키가 기록에서 빠지지 않는다. 기록 쓰기가 실패하면 액터는 그 뒤 입력을 막는다(대기 요청 취소, 눌린 키만 떼고 더 기록하지 않음) — 반쯤 쓴 줄 뒤에 이어 쓰면 읽기가 그 줄을 버려 실제로 누른 키가 빠지기 때문이다
- **기록 작성자는 runner 하나**다. 이벤트마다 `seq`를 붙여 `events.jsonl`에 쓰고, daemon은 파일을 구독해 UI에 다시 보낸다. UI가 느리거나 끊겨도 runner는 멈추지 않는다. UI는 다시 붙을 때 마지막 `seq` 이후를 요청한다. 이 커서는 **UI가 실제로 적용한 마지막 `seq`**다(daemon이 보냈다고 알린 `seq`가 아니다: 송신 큐에 넣었지만 보내지 못한 이벤트가 있을 수 있다). daemon은 구독마다 보낸 마지막 `seq`(hwm)를 두고, 과거분을 보내는 동안 들어온 실시간 이벤트는 보류했다가 `seq > hwm`인 것만 이어 보내므로 같은 `seq`가 두 번 가거나 역행하지 않는다. 송신 큐가 차면 `run.lagged`를 보내고 그 구독을 끊는다. UI는 적용한 마지막 `seq`로 다시 구독한다. 감독자 마무리(`run.end` 뒤의 `input.recovered` 포함)까지 보낸 뒤에 `run.ended`를 보낸다. runner가 죽은 실행은 프로세스 종료를 확인한 뒤 **감독자만** 마무리 기록을 쓴다(runner 쪽에 복구 프로세스를 두지 않는다 — 한 실행에 감독자는 하나이므로 복구 작성자도 하나다)
- **프로세스 정리**: 실행마다 Windows Job Object를 만들어 우리가 띄운 runner·worker·보조 프로세스를 넣는다. `core.app.launch`로 띄운 게임은 넣되, `core.window.attach`로 붙은(사용자가 미리 띄운) 게임은 넣지 않는다. Job 종료가 키 해제를 대신하지는 않는다
  - Job 수명: 감독자가 이름 있는 Job(`Local\Kookabug.Run.<run_id>`)을 "마지막 핸들이 닫히면 안의 프로세스를 끝냄"(`KILL_ON_JOB_CLOSE`)으로 만들고, runner는 시작하자마자(어떤 자식도 띄우기 전에) 그 Job을 이름으로 열어 자기를 넣는다. 그래서 핸들이 둘이고, **둘 다 닫혀야** OS가 Job을 정리한다. 감독자만 죽으면 runner가 취소 순서를 밟고 끝나며 runner의 핸들이 마지막으로 닫혀 남은 워커가 끝난다. runner만 죽으면 감독자가 마무리한 뒤 Job을 끝낸다. 둘 다 죽으면 OS가 정리한다
  - Job 핸들은 상속하지 않고 다른 프로세스에 넘기지 않는다. runner 뒤에 띄운 워커는 생성 시점부터 Job 소속이라 "띄운 뒤 넣기" 사이의 경쟁이 없다
- **워커**: venv는 재사용하지만 워커 프로세스는 실행마다 새로 띄운다. 실행 중에는 플러그인 설치로 그 환경을 바꾸지 않는다
  - 실행 위치: 코어 노드(`core` 플러그인)는 runner 안에서, 그 밖의 플러그인 노드는 워커에서 실행한다. 워커 호스트는 SDK(`python -m kookabug_sdk.worker`)에 있어 플러그인 venv에 본체 의존성을 들이지 않는다. 캡처·OCR 격리는 별도 프로세스가 아니라 **관측 호출의 유효 기한**으로 한다: 캡처·찾기·OCR 호출 하나의 기한 = `min(설정 기한, 노드 기한 남은 시간, 전체 기한 남은 시간)`이고, 노드 기한이면 `ObservationTimeout`(노드의 `timeout` 출구), 설정 기한이면 `capture_timeout`, 전체 기한이면 `deadline_exceeded`. 기다리는 동안 50 ms마다 취소를 확인하고, 그래도 멈춘 관측은 M0b 하드 종료·복구 경로가 처리한다. 워커는 참조 이미지를 받고 픽셀 관측은 runner에 요청한다(위 "큰 데이터")
  - 시작 순서: 실행 스냅샷 → 워커를 띄워 `worker.hello` → 원격 노드 등록 → 그래프 의미 검증. runner는 플러그인 코드를 import하지 않고 hello로 받은 노드 스키마로 검증한다. hello가 기한(`run.worker_start_timeout_ms`, 기본 30초) 안에 오지 않거나 그 전에 워커가 죽으면 실행은 `error`(`worker_start_timeout`·`worker_died`)이고, 기다리는 동안에도 취소·전체 기한이 먹힌다
  - 입력·캡처·기록·변수·설정은 **runner가 한다**: 워커의 `ctx` 호출은 runner에 요청으로 오고, runner 주 스레드가 노드 응답을 기다리는 동안 그 요청을 처리한다. runner는 요청을 그 노드의 선언(`pure`·`effects`)으로 다시 검사하고, 노드 결과도 선언과 다시 대조한다 — 워커를 믿지 않는다. `ctx` 요청은 자기를 부른 노드 실행의 번호(`invoke`)를 싣고, runner는 지금 기다리는 실행의 번호가 아닌 요청(노드가 보관해 둔 이전 `ctx`, 남긴 스레드의 늦은 요청)을 처리하지 않는다 — 다음 노드의 선언·기록 정책으로 처리되면 안 된다
  - **입력은 공용 입력 서비스를 거친다** (M1): 워커의 `ctx.input.*` 요청도 코어 노드의 입력과 같이 그 스텝 ctx → 공용 입력 서비스(요청 창 고정, `match` 재검증·다시 찾기 — [[그래프 JSON 스키마 v0]] 6장) → 입력 액터 큐로 간다. 재검증 실패는 오류 종류 `stale_observation`으로 답하고 워커에서 같은 예외(`StaleObservation`)가 된다. 노드가 그것을 삼키고 끝내도 runner가 그 스텝을 처리되지 않은 fail로 본다
  - **관측 RPC의 기한**: 캡처·찾기·OCR·창 기다리기 요청은 노드 기한의 남은 시간(`deadline_ms`)을 싣고, runner는 위 유효 기한 규칙을 자기 시계로 다시 적용한다. 노드 기한으로 끝나면 오류 종류 `observation_timeout` → 워커의 `ObservationTimeout`(노드의 `timeout` 출구). 기한이 이미 지났으면 워커는 요청하지 않는다. runner 쪽 오류 코드(`frame_expired`·`window_gone`·`capture_timeout` 등)는 워커에서 `RunnerError(code)`이고, 노드가 잡지 않으면 runner는 **그 실행에서 자기가 낸 코드일 때만** 그 코드로 스텝을 끝낸다(아니면 `node_error`)
  - `ctx.path()`는 원본 워크스페이스가 아니라 **실행 스냅샷 루트**(`<실행 폴더>/snapshot`) 기준이다. 실행 내내 같은 파일을 읽는다
  - 값은 JSON으로 옮기고 SDK 타입은 `{"$kb": 태그}`로 표시한다. 비밀값은 경계 너머에서도 비밀값이다(원문은 인증된 파이프로만)
  - 실행 중 워커가 죽으면 그 스텝은 `error`(`worker_died`, 종료 코드)이고 다시 띄우지 않는다

### 취소 순서

1. 입력 차단 = 입력 액터의 게이트 닫기 (새 입력 요청 거부, 큐에서 기다리던 요청도 취소)
2. 키 해제 = 액터 큐 맨 앞에 release_all. 액터가 지금 하던 동작 하나를 끝내는 대로 이번 실행이 누른 키·마우스 버튼을 누른 차례의 거꾸로 뗀다. 취소를 받은 스레드는 입력 장치를 직접 부르지 않는다. 떼기는 입력 직전 확인(포그라운드·점 아래 창 등)을 거치지 않는다 — 게임이 포커스를 잃었어도 뗀다
3. 워커에 취소 요청 → 기한 안에 응답 없으면 워커 종료
4. 기록 확정 (`step.end` 중단 표시, 실행 결과)
5. runner 종료

runner가 이 순서를 못 밟고 죽으면 감독자가 2·4를 대신한다. 감독자도 없으면 다음 입력 임대권 획득자가 2를(입력하기 전에), 다음 기록 읽기가 4를(`run.end`·`step.end`가 없으면 "중단") 대신한다. 감독자가 키를 해제하려면 runner가 "지금 누르고 있는 키"를 이벤트로 남겨야 한다 (`input.down` / `input.up`).

감독자의 **복구 경로**는 runner가 어떻게 끝났든(정상·하드 종료·kill·크래시) 한 번 밟고, 다시 밟아도 결과가 같다: runner 종료를 프로세스 식별(PID + 생성 시각)로 확인 → 기록 끝의 잘린 줄 자르기 → 기록상 눌렸을 수 있는 키를 입력 임대권 안에서 해제(실행과 같은 입력 장치 — 실제 실행이면 SendInput, 누른 차례의 거꾸로, 확인 없이. 마우스 버튼은 그 순간 커서 자리에서 뗀다) → `run.end`가 없을 때만 `run.end`(`runner_died`) → 영상 마무리(`finalize_video`, 저널의 최종 `run.end` 기준 — M3) → `run.json`을 `run.end`에 맞춰 다시 만듦(영상 요약은 `video/index.json`에서) → Job 정리. 종료를 확인하기 전에는 아무것도 쓰지 않는다. runner가 쓴 `run.end`는 덮어쓰지 않고, 열린 스텝에는 `step.end`를 쓰지 않는다("중단"). 감독자는 runner가 시작 인사(`runner.hello`)를 기한 안에 하지 못해도 runner를 끝내고 같은 경로로 마무리한다.

- **취소 사유**: `cancelled`(외부 취소) · `deadline_exceeded`(테스트 전체 기한) · `supervisor_lost`(감독자 사망). 먼저 정한 사유가 남고 `cancel.requested`·`run.end.cancel_reason`에 적는다. 기한 초과로 끝난 스텝은 `error`(`deadline_exceeded`), 나머지 취소는 `cancelled`
- **runner 안의 역할**: 노드는 주 스레드가 실행하고, 제어 스레드가 감독자 요청(취소·멈춤·재개)을 받는 즉시 답한다. 제어 스레드는 취소 순서를 시작만 한다(종료 단계 진입을 감시자에 알림 → 취소 토큰 → 액터 게이트 → 워커 취소 → 감독자에 `runner.stopping` → `cancel.requested`). 마무리(`run.end`·`run.json`·임대권 놓기)는 주 스레드 하나만 한다
- **기한 감시**: 제어 스레드가 runner 시작부터 잰 전체 기한에 취소 순서를 `deadline_exceeded`로 시작한다. 워커 노드도 취소 유예 뒤 끊긴다. M3부터 전체 기한은 runner의 **활성 시계**(단조 시간 − 멈춘 시간, 멈춘 동안 머묾)로 잰다. 제어 스레드와 실행기 런타임(전체 기한·노드 기한·기다림)이 같은 시계 하나를 보므로 디버거로 멈춘 시간은 두 기한에서 함께 빠진다(한쪽만 빼면 멈춘 채 `deadline_exceeded`가 난다). 경과(`duration_ms`)는 실제 단조 시계로 따로 잰다. 취소 뒤의 유예(워커 취소 유예·마무리 유예·자기 종료 감시자)와 관측 호출의 설정 기한은 실제 시간 그대로다. 주 스레드가 판정을 확정해 마무리(녹화 정리·`run.end`·`run.json`)를 시작하면 전체 기한 감시는 끝난다: 마무리는 판정을 바꾸지 않으므로 그 사이 기한이 지나도 취소 순서·`cancel_reason`을 붙이지 않는다(제어 스레드가 기한을 본 직후 확정돼도 확정 뒤에는 시작하지 않는다). 마무리의 실제 시간 유예(하드 종료·자기 종료 감시자)·감독자 사망 감시·외부 취소는 그대로이고, 마무리 시간도 `duration_ms`·`active_duration_ms`에 그대로 든다
- **하드 종료**: 감독자는 취소를 보냈을 때, 또는 runner가 종료 단계에 들어갔다고 알렸을 때(`runner.stopping`: 기한 초과·감독자 사망 취소·정상 마무리 시작)부터 마무리 유예(`shutdown_grace_ms`, 기본 5초)가 지나도 runner가 살아 있으면 runner를 강제 종료하고 복구 경로를 밟는다. 제어 채널을 잃은 감독자도 곧바로 강제 종료한다(단 `runner.stopping`을 받은 뒤의 채널 끊김은 runner가 마무리 끝에 채널을 닫은 것일 수 있으므로 마무리 유예 타이머에 맡긴다). runner는 이 타이머보다 먼저 마무리를 끝내도록 녹화 스레드 기다림을 줄인다. 기다림은 처음 보낸 `runner.stopping`부터 3초까지이고, **실제로 적용되는 가장 이른 종료 기한**에서 기록 여유를 뺀 때를 넘지 않는다. 종료 기한은 다음 셋 중 가장 이른 것이다(`Controller.finish_by`).
  - 감독자가 `run.cancel`로 알린 하드 종료 기한. 감독자는 이미 건 타이머가 끝내는 **절대 단조 시각**(`hard_stop_at_mono`, Python `time.monotonic` 초)과 보내기 직전에 잰 남은 시간(`hard_stop_in_ms`)을 보낸다.
    - **계약**: 감독자와 runner는 같은 Windows PC의 프로세스이고, `time.monotonic`은 시스템 전역 `QueryPerformanceCounter`라 원점이 같다(Python 3.13부터 Windows `monotonic`이 QPC). 그래서 절대 시각은 송신·수신·처리 지연과 상관없이 정확하다.
    - runner는 그래도 그대로 믿지 않는다. `min(절대 시각, 요청을 꺼낸 시각 + 남은 시간)`을 써서 어느 쪽도 늦게 잡지 않는다. 절대 시각이 이미 지났거나 꺼낸 시각 + 유예보다 멀면(감독자는 꺼내기 전에 타이머를 걸었으므로 계약대로면 그럴 수 없다 — 시계 원점이 다르다고 본다) 녹화를 기다리지 않고 바로 기록한다.
    - 절대 시각 없이 남은 시간만 오면(계약 밖의 호출자) 꺼낸 시각 + 남은 시간을 쓴다. 이때는 전달 지연만큼 늦게 잡힐 수 있고 상한이 없다.
  - 감시자가 알아챈 감독자 사망 + 유예(자기 종료).
  - 처음 보낸 `runner.stopping` + 유예. 영상 마무리 단계를 허락받았으면 감독자가 다시 건 기한.

  기록 여유는 1초이고, 유예가 2초보다 짧으면 유예의 절반이다(6장 M3 영상 마무리). 그래서 runner가 취소를 늦게 처리했거나 사용자가 유예를 4초보다 짧게 정해도, 영상을 포기한 뒤 `run.end`·`run.json`·임대권 놓기를 하드 종료 전에 끝낸다. 먼저 건 하드 종료 타이머는 미루지 않는다. 마무리의 기다림(워커 종료·액터 멈춤·녹화 스레드)은 시작할 때 정한 고정 예산이 아니라 그때 아는 가장 이른 종료 기한에서 기록 여유를 뺀 때까지다. 기다리는 도중 더 이른 기한이 알려지면 바로 줄인다. 예를 들어 정상 판정 뒤 녹화를 기다리는 중에 외부 취소가 도착하거나 감독자가 죽으면, 제어기가 기한 갱신 신호를 세우고 녹화 기다림이 깨어 다시 잰다. 녹화 스레드가 끝나도 같은 신호가 선다. 워커는 프로세스 대기를, 액터는 스레드 대기를 20·50 ms 단위로 나눠 기한을 다시 읽는다. 보장 범위는 감독자 계약대로 절대 시각이 오는 경우다: 전달·처리 지연이 얼마든 기한을 늦게 잡지 않는다. 기록 여유(1초)는 녹화를 포기한 뒤 `run.end`·`run.json`·임대권 놓기에 쓰는 시간이고, 전달 지연을 덮는 데 쓰지 않는다. 마무리 자체가 기록 여유보다 오래 걸리면(프로세스가 굶는 등) 하드 종료가 날 수 있고, 그때는 감독자 복구가 마무리한다. 대신 인코더를 닫는 데 그 기다림보다 오래 걸리는 실행은 영상을 잃는다(`encoder_stuck`)
- **영상 마무리 단계** (M3 사람 확인 R1 F1 3라운드): 실행이 인코더 열기 시험보다 먼저 끝나 녹화 스레드가 실행 중 모은 프레임을 들고 시험을 기다리면(늦은 인코더 대기 — 멈춘 것이 아니다), runner는 `encoder_stuck` 없이 `run.end`를 쓴 뒤(판정·종료 코드는 여기서 확정) 감독자에게 `runner.video_finishing{wait_ms}`을 청한다. 감독자는 실행마다 한 번만, 외부 취소를 받지 않았고 하드 종료하지 않았으면 허락하고 하드 종료 타이머를 지금 + `wait_ms`(최대 30초) + 유예로 다시 걸어 그 기한을 답한다. runner는 그 기한을 종료 기한으로 쓰고 자기 종료 감시자도 그 기한 + 여유로 미룬 뒤, 상한 안에서 시험과 모은 프레임 쓰기를 기다린다. 끝나면 평소처럼 `finalize_video`·`run.json`. 다음이면 녹화 스레드에 포기를 알리고 그 실행의 영상을 `status: omitted`/`encoder_not_ready`(실행 끝까지 `starting` 빈 구간 `reason: encoder_not_ready`)로 남긴다: 상한 초과, 남길 까닭이 없음(`failed_only` 프레임뿐인데 `pass`·`skipped`·사용자 취소 — 통과 실행은 기다리지 않는다), 실행이 외부 취소·감독자 사망으로 끝남, 감독자 거절·무응답. 단계 중 외부 취소가 오면 감독자가 타이머를 지금 + 유예로 당기고(`run.cancel` 기한) runner는 기다리지 않고 바로 포기한다. 감독자가 죽으면 사망 + 유예가 새 기한이라 runner가 바로 포기하고 그 안에 마무리한다. 녹화 스레드는 대기에 들어갈 때 표식(`video/encoder-wait.json`, `phase: waiting`)을 남기고, 준비가 끝나면 `writing`으로 바꾸며, 표식은 단계만 알리고, 결과가 정해졌다는 근거는 덧붙이기만 하는 저널(`segments.jsonl`) 하나다: 모은 프레임의 쓰기·닫기 결과(조각·포기 빈 구간·`failed`·`unavailable`)를 모두 적는 데 성공하면 한 곳(`_settle_late`)에서 같은 저널에 완료 줄(`encoder_wait: settled`)을 덧붙이고, 표식 지우기는 그 뒤의 최선 시도다. 공통 판정(`abandoned_reason`)은 완료 줄이 있으면 표식을 무시하므로 Windows 읽기 핸들이 표식 삭제·교체를 막아도 판정이 바뀌지 않고, 마무리의 임시 파일 정리도 판정 뒤에 한다. 결과나 완료 줄을 적지 못하면 표식이 남아 감독자 마무리가 포기 이유를 낸다. 그래서 준비가 끝난 뒤 쓰기가 멈춰 상한을 넘기거나 단계 중 하드 종료돼도, 감독자 마무리가 표식 단계로 `encoder_not_ready`(`waiting`)·`encoder_stuck`(`writing` — `video/`를 모두 지움)을 정한다. 쓰다 만 조각을 지운 기록이 있어도 `recorded`가 되지 않는다. 작성자를 기다리다 포기한 runner의 `run.json` 영상 요약은 그 마무리를 파일을 건드리지 않고 같은 함수로 미리 계산한 것이라 복구 뒤와 같다(`abandoned_reason`·`preview_video`). `run.end`는 뒤늦게 고치지 않는다. 실행 기한(`deadline_ms`)·판정·종료 코드·`run.end` 이후 기록 규칙은 그대로이고, 늦어지는 것은 runner 프로세스가 끝나는 때(최대 30초)뿐이다
- **자기 종료 감시자**: runner 안의 전용 스레드로, 잠금·기록·통신을 쓰지 않고 OS 대기와 `TerminateProcess(self)`만 한다. 감독자가 죽은 뒤 마무리 유예가 지나도, 또는 감독자가 살아 있는데 종료 단계 진입 뒤 마무리 유예 + 여유(10초)가 지나도(영상 마무리 단계를 허락받았으면 감독자가 다시 건 기한 + 여유) runner가 살아 있으면 끝낸다. 조건이 "마무리를 시작했는가"가 아니라 "프로세스가 아직 살아 있는가"라서, 주 스레드가 기록 잠금을 쥔 채 멈추거나 입력 장치 호출에서 멈춰도 끝난다

| 상황 | 끝내는 주체 | 키·기록 |
|---|---|---|
| 정상 종료, 취소·기한을 주 스레드가 유예 안에 마무리 | runner 주 스레드 | 주 스레드 (액터가 멈춘 뒤 임대권을 깨끗하게) |
| 취소·기한·정상 마무리 중 주 스레드·액터가 멈춤 | 감독자 하드 종료 (뒤 안전망: 자기 종료 감시자) | 감독자 복구 경로 |
| 제어 채널 끊김, 감독자 생존 | 감독자가 runner 강제 종료 | 감독자 복구 경로 |
| 감독자 사망, runner 정상 | runner 스스로 취소 → 정상 마무리 | runner 주 스레드 |
| 감독자 사망, runner 멈춤 / 둘 다 사망 (이중 고장) | 자기 종료 감시자 또는 OS (Job 마지막 핸들) | 그 자리에서 복구 없음: 키는 다음 임대권 획득자, 기록은 다음 읽기가 "중단" |
| runner kill·크래시 | — | 감독자 복구 경로 |

### 입력 임대권

- 하나의 Windows 사용자 세션에서 **입력을 보낼 수 있는 주체는 하나**다: 실행 / 녹화 / MCP 직접 제어 중 하나
- Windows 이름 있는 뮤텍스(`Local\Kookabug.InputLease`)로 구현한다. 소유 프로세스가 죽으면 OS가 풀어 준다. 소유자 정보(종류, 워크스페이스, 실행 ID·폴더, 프로세스 식별)와 "깨끗하게 놓았는가"(`clean`)는 옆 파일(`%LOCALAPPDATA%\Kookabug\input-lease.json`)에 적는다. 뮤텍스는 스레드 소유이므로 **전용 스레드**가 얻고 같은 스레드가 놓는다
- **얻을 때 앞 소유자 복구**: 얻은 직후 옆 파일을 보고 앞 소유자가 깨끗하게 놓지 않았으면, 입력하기 **전에** 앞 실행 기록에서 눌렸을 수 있는 키를 떼고 앞 실행 폴더에 복구 표시(`input-recovery.json`)를 남긴다. 표시가 이미 있으면 다시 떼지 않는다. 뮤텍스의 "버려짐(abandoned)"은 그때 다른 핸들이 열려 있어야만 보이므로 판단 근거로 쓰지 않는다
- **깨끗한 놓기는 입력 액터가 멈춘 뒤만**: 액터가 큐를 비우고 끝났고 눌린 키가 없을 때만 옆 파일을 `clean`으로 쓰고 놓는다. 그 밖의 종료(멈춘 액터, 하드 종료, kill)는 놓지 않은 채 끝나고 다음 획득자가 복구한다
- **감독자의 키 복구도 임대권 안에서만** 한다. runner가 죽은 뒤 감독자는 복구 표시가 있으면 건너뛰고, 없으면 임대권을 얻어(얻기 복구가 그 실행을 뗀다) 곧바로 깨끗하게 놓는다. 기한 안에 못 얻으면 지금 소유자가 이미 복구했어야 하므로 표시를 다시 본다. 그래서 감독자의 늦은 복구가 다음 실행의 입력을 건드리지 않는다
- **이중 고장**(감독자와 runner가 둘 다 죽거나 멈춤): 그 자리에서 키를 떼는 주체는 없다. 다음 임대권 획득자가 입력 전에 뗀다. 그때까지 키가 눌려 있을 수 있다
- 얻기 복구·감독자 복구의 떼기는 입력 직전 확인 없이 **그 실행의 입력 장치**로 한다(가짜 플랫폼은 같은 기록 파일, `windows`는 SendInput). 그래서 옆 파일의 소유자 정보에 입력 장치를 함께 적고, 다음 획득자는 자기 장치와 다르면 그 장치의 백엔드를 따로 만들어 뗀다(실제 실행이 남긴 키를 가짜 실행이 "뗐다"고 표시하거나, 가짜 키를 실제 장치로 떼지 않게). 떼기가 실패하면 복구 표시를 남기지 않는다(다음 획득자가 다시 뗀다)
- **녹화 주체** (M4): 녹화 세션 동안 daemon이 임대권을 쥔다. 소유자 종류 `recorder`, 실행이 없어 실행 ID·폴더는 null, 입력 장치는 `none`(녹화는 입력을 보내지 않는다). 녹화 시작 준비(`starting`)부터 녹화·일시정지 동안 쥐고, 정지해 훅·캡처를 닫은 뒤 깨끗하게 놓는다(눌린 키가 없음이 자명하다). daemon이 녹화 중 죽으면 다음 획득자는 앞 소유자의 장치가 `none`이라 뗄 것 없이 복구 표시만 남긴다. 같은 daemon의 실행 요청(`run.start`)은 녹화가 `starting`·`recording`·`paused`인 동안 runner를 띄우기 전에 `recording_active`로 거부하고(실행 시작과 녹화 시작 예약이 같은 잠금 안에서 판정), 다른 daemon·CLI 실행은 임대권에서 `input_lease_busy`로 끝난다
- MVP는 이미 다른 주체가 갖고 있으면 **명시적으로 거부**하고 누가 갖고 있는지 알려 준다. 대기·양보는 이후 버전
- 디버거로 멈춘 실행도 임대권을 유지한다. 그동안 Agent가 직접 클릭하려면 실행을 끝내야 한다

### MCP

- 활성 툴셋은 **에이전트 연결별** 상태다
- `kb_graph_patch`는 기준 revision을 받는다. 그 사이 UI나 다른 연결이 고쳤으면 거부한다. 연산(M5): `add_node`·`set_node`·`remove_node`·`connect`·`disconnect`·`link`·`unlink`·`move`·`set_meta` — 한 번에 모두 적용하거나 하나도 안 함, 새 노드 ID는 daemon이 정함 (daemon `graph.patch`)
- `kb_run_start`는 중복 방지 키를 받는다. 연결이 재시도해도 실행이 두 개 생기지 않는다

## 4. 배포

- Windows 설치 파일: electron-builder v26(NSIS) + electron-updater + GitHub Releases
- **M1(CLI만)**: Inno Setup 6 사용자별 설치 파일(관리자 권한 없음, `%LOCALAPPDATA%\Programs\Kookabug`, 사용자 `PATH`에 `bin`, 제거 등록). 폴더는 `python\`(PBS + 미리 설치한 wheel + 앱 로컬 VC++ 런타임) · `bin\kookabug.exe` · `ocr-models\` · `examples\sample-game\` · `licenses\` · `VERSION`. M2부터 NSIS로 바꾸고 폴더 구조는 유지한다 (`tools/installer/`)
  - **VC++ 런타임은 앱 로컬**: PBS에 `msvcp140.dll`이 없고 opencv·onnxruntime이 요구한다. 빌드 머신 Visual Studio의 `VC\Redist`에서 `msvcp140*`·`vcruntime140*`·`concrt140`을 `python.exe` 옆에 복사한다. 설치 트리의 모든 `.pyd`·`.dll`·`.exe` import를 Windows가 실제로 찾는 곳(그 파일 폴더·앱 폴더·System32)과 등록 근거가 확인된 DLL 폴더(패키지가 `os.add_dll_directory`로 더하는 `numpy.libs` 등, 그 패키지 안 파일에만)로만 풀어 보는 DLL 검사가 VC++ 런타임이 설치 폴더에서 풀리는지 확인한다. 설치 폴더 어딘가에 같은 이름이 있다는 것만으로는 통과시키지 않는다
  - **실행기**: uv가 만든 콘솔 실행기의 Python 경로 자원을 빌드 때 상대 경로(`..\python\python.exe`)로 바꾼다. 실행기는 상대 경로를 자기 폴더 기준으로 풀므로 설치 뒤 다시 만드는 단계가 없고 폴더를 옮겨도 돈다. 실행기 스텁에 정적으로 든 크레이트는 빌드에 쓰는 uv 판(고정, 빌드가 확인)의 `Cargo.lock`으로 만든 레포 SBOM과 원문으로 감사한다
  - **테스트 판**: 무인 설치 검사는 AppId·이름·기본 폴더·제거 등록 이름이 모두 다른 테스트 전용 판만 설치하고 HKCU 제거 등록이 끝에 처음과 같은지 본다. 개발자 PC의 실제 설치를 건드리지 않는다
  - **빼는 것**: `opencv-python`의 FFmpeg DLL(LGPL), PBS의 pip·`ensurepip`·`idlelib`. 파일과 그 `RECORD` 줄을 지우고 최종 트리 감사가 남은 것이 없는지 본다. 제거 목록은 감사 표(`[[strip]]`) 하나다
  - **영상(M3)은 새 바이너리가 없다**: H.264 MP4는 사용자 PC의 OS 구성요소(Windows Media Foundation H.264 인코더)를 이미 감사한 `cv2.pyd`의 MSMF 백엔드로 부른다(`cv2.CAP_MSMF` 명시 — FFmpeg 백엔드로 넘어가지 않는다). 인코더는 배포물에 들지 않아 설치 트리·라이선스 감사가 그대로이고, NOTICES의 "OS 구성요소 사용" 절에 이 근거를 적는다. 재생은 앱 `<video>`(Electron 배포물 그대로)다. Media Foundation이 없는 Windows(N·KN 판에서 미디어 기능 팩 없음, Server Core)는 영상 없이 실행한다: 인코더는 녹화를 시작할 때만 열고(import 때 MF를 건드리지 않음), MF DLL 로드 실패·OpenCV MSMF 백엔드 없음·열기 실패를 `unavailable`(이유 `mf_missing`·`backend_missing`·`encoder_open_failed`)로 모으며 runner·daemon·앱·doctor 기동은 계속한다. 설치본 검사가 사용 불가를 주입해 헤드리스 그래프·앱 스모크를 돌린다
  - 설치 폴더 + 가장 긴 상대 경로가 260자(MAX_PATH)를 넘으면 설치 파일이 복사 전에 멈춘다 (onnxruntime 안 경로가 약 150자)
- **M2(데스크톱 앱)**: electron-builder 26 NSIS로 바꿨다. 사용자별 설치(관리자 권한 없음, 설치 범위 고르기 화면은 설치·제거 프로그램에 넣지 않음 — `packaging/no-install-mode-page.nsh`, 빌드가 컴파일 표식으로 확인)·`%LOCALAPPDATA%\Programs\Kookabug`·사용자 `PATH`에 `bin`·시작 메뉴 바로 가기는 M1과 같고, M1 폴더 구조에 앱(`Kookabug.exe`, `resources\app.asar`, Electron 배포물)을 더했다. 설정은 `apps/desktop/electron-builder.yml`과 NSIS 조각 `apps/desktop/packaging/installer.nsh`, 빌드는 `tools/installer/build.py`
  - **감사한 트리 그대로 묶는다**: 스테이징(M1 구조) → electron-builder `--dir`(Electron + 앱 배포 빌드 + 스테이징을 `extraFiles`로) → 그 트리에 최종 트리 감사·NOTICES → 같은 트리로 `--prepackaged` NSIS. 앱 번들은 배포 빌드(`build:release`)라 E2E 검사 훅이 없고, 빌드와 설치 스모크가 묶음 안 번들로 확인한다. daemon이 선택 설치로 쓰는 `kookabug-platform`을 포함해 우리 패키지가 다 들어갔는지 빌드가 본다
  - **Electron 네이티브 감사**: 설치 폴더에서는 DLL·exe와 함께 Electron 바이너리 자원(`.pak`·`.dat`·`.bin`·`.asar`)도 네이티브 표에 있어야 한다. 실행 파일·자원 묶음은 Electron의 `LICENSES.chromium.html`(모든 빌드 구성의 credits, 약 20 MB)과 `LICENSE.electron.txt`를 원문으로 쓰고, credits는 크기 때문에 NOTICES에 옮겨 싣지 않고 위치만 적는다(설치 폴더에 그대로 있다). `d3dcompiler_47.dll`·`dxil.dll`은 Microsoft 재배포 파일(`LicenseRef-*`). 기본 앱(`default_app.asar`)과 판 파일(`version`)은 넣지 않는다
  - **ffmpeg.dll(LGPL-2.1)**: Electron이 이 DLL 없이 시작하지 않아 뺄 수 없다. 허용 목록의 **고정 바이너리 한정 예외**(`[[pinned_binary]]`)로만 허용한다: 배포물 판(설치 트리의 실행 파일에서 읽은 Electron 판)·설치 폴더 안 상대 경로·sha256이 모두 맞는 그 파일 하나다. 판정기는 거부 패턴보다 먼저 보되 하나라도 다르면 금지 그대로이고, 같은 이름의 다른 DLL·opencv의 FFmpeg·다른 LGPL 구성요소는 여전히 막힌다. LGPL-2.1 원문은 NOTICES에, 그 빌드에 대응하는 소스·패치·빌드 설정의 판 고정 위치와 제공 방법은 배포 산출물 `licenses\ffmpeg-SOURCE.txt`에 둔다(예외가 서려면 설치 트리에 있어야 한다). Electron을 올리면 예외와 그 파일을 새로 만든다 (사용자 결정 U8 기본값)
  - **설치 파일에 LGPL 플러그인을 넣지 않는다**: 앱 묶음은 zip(nsisunz 플러그인)이다. 7z 묶음은 nsis7z(7-Zip, LGPL-2.1)가 들어간다. electron-builder 기본 스크립트가 부르는 StdUtils(LGPL-2.1) 함수는 NSIS 조각이 System 플러그인·NSIS 명령으로 바꿔 정의해 플러그인이 컴파일되지 않는다. 차등 업데이트 묶음·설치 파일 사본은 만들지 않는다(자동 업데이트는 배포 단계)
  - **사용자 PATH**: 레지스트리 값을 형식과 크기까지 먼저 읽고, 읽지 못하거나(다른 형식·오류) NSIS 문자열 한도에 닿거나 더한 결과가 한도를 넘으면 고치지 않고 안내만 한다(설치는 계속). 더할 때는 끝에 `;<bin>`만 붙이고 원래 형식(REG_SZ/REG_EXPAND_SZ)으로 쓴다. 제거는 이 설치가 더한 경우(설치 정보 키의 기록)에만 그 항목과 붙인 구분자 하나를 빼서, 다른 항목·빈 항목·구분자·형식·값의 존재가 설치 전과 바이트 단위로 같다 (`apps/desktop/packaging/user-path.nsh`)
  - **실행 중인 앱 끄기**: 설치·제거는 설치 폴더 + `\`로 시작하는 실행 파일의 프로세스만 찾아 끈다. electron-builder 기본 확인은 PowerShell이 없으면 실행 파일 이름으로 `taskkill /IM`을, 있어도 경계 없는 앞부분 비교를 해서 다른 판·다른 폴더의 앱을 끌 수 있다. 확인할 수 없으면 아무것도 끄지 않고 멈춘다
  - 실행 파일·설치 파일·시작 메뉴 바로 가기는 확정 앱 아이콘 A1(`Docs/Design/앱 아이콘 (L3)/확정 A1/kookabug.ico`)을 쓴다. 빌드가 ICO의 이미지가 모두 들어갔는지 본다
  - **테스트 판**: appId·이름·GUID(제거 등록 키)·기본 폴더·실행 파일 이름(`KookabugTest.exe`)이 모두 다르다. 실행 파일 이름·버전 정보가 달라 최종 트리는 판마다 만들어 감사한다. 무인 설치 검사는 HKCU 제거 등록 전체·`HKCU\Software\<GUID>`·시작 메뉴 바로 가기·사용자 PATH(값·형식·존재)가 끝에 처음과 같은지 보고, PATH는 따로 백업해 다르면 되돌린다. 제품 판 실행 파일 이름의 대역 프로세스를 설치 폴더와 이름 앞부분이 같은 옆 폴더에 띄워 두고 설치·제거 뒤에도 살아 있는지 본다. 제거는 폴더뿐 아니라 그 판의 등록·바로 가기 정리가 끝날 때까지 기다린다(NSIS는 폴더를 먼저 지운다). 앱 스모크(`--smoke <예제 워크스페이스 사본>`: daemon·`session.hello`·`graph.open`·무수정 `graph.save`(`wrote: false`)·`daemon.shutdown`)는 임시 사용자 데이터 폴더로 돌린다
  - 제거는 설치한 맨 위 항목만 지우고(사용자가 고른 폴더의 다른 파일은 남김) 폴더가 비면 그것도 지운다
- Python 런타임은 **앱에 포함**한다 (python-build-standalone + 코어 의존성 미리 설치). 플러그인 의존성 설치용 uv도 포함한다 — M1 설치본에는 넣지 않는다(플러그인 설치가 생길 때, `uv.exe`에 정적으로 들어간 크레이트들의 라이선스 원문과 함께)
- CLI만 쓰는 CI용으로 PyPI 배포 (`pip install kookabug`)
- **라이선스 감사는 M0부터 CI**에서 한다: Python 의존성(pip-licenses), JS 의존성, python-build-standalone 배포물에 들어 있는 라이선스 메타데이터, OCR 모델·사전 파일. 결과를 설치 파일의 `THIRD_PARTY_NOTICES`로 묶는다
  - **네이티브 파일도 구성요소별로** 본다: wheel·Python 배포본 안의 DLL·pyd·exe는 전부 `tools/native-licenses.toml`의 항목(파일 glob → 그 파일에 정적으로 들어간 구성요소 전부의 SPDX 식·이유)에 맞아야 하고, 식의 모든 부분이 허용이어야 한다. **식의 모든 구성요소에 라이선스 원문이 연결돼야 한다**: 배포물 안 파일이나 레포 `tools/third_party_licenses/`의 원문, 원문마다 반드시 있어야 하는 글귀로 확인하고 NOTICES에 그대로 싣는다. Rust 확장은 동봉 SBOM의 크레이트마다 원문 절이 있어야 한다(`tools/fetch_crate_licenses.py`가 crates.io에서 모은다). SPDX 밖 배포 조건(VC++·DirectX 재배포 파일·NSIS 플러그인·sqlite blessing·Intel IPP·Chromium credits)은 원문 위치와 처리 근거를 적은 `LicenseRef-*`로 그 표에서만 허용한다. 조건부 라이선스(MPL-2.0)가 DLL 안 구성요소이면 그 네이티브 항목의 이유를 예외 근거로 삼는다
  - **두 단계**: 빌드 입력 감사(감사 venv·설치 전 트리 — 금지 라이선스 파일·표에 없는 파일은 제거 목록에 있을 때만 허용, 제거 glob이 아무것도 못 맞히면 실패)와 최종 설치 트리 감사(제거 목록과 무관하게 금지 파일이 남으면 실패, 모든 네이티브 파일이 표에 맞아야 함, `dist-info/RECORD`와 실제 파일이 서로 맞아야 함, 설치본 `ocr-models/` 안의 모델·라이선스 근거 원문 해시, 근거 원문은 NOTICES에 실음). 설치 파일 빌드는 설치 파일에 들어갈 트리(M2: electron-builder `win-unpacked`)에, CI는 무인 설치 결과에도 최종 트리 감사를 건다. 설치 프로그램이 설치 때 더하는 파일(NSIS 제거 프로그램)은 설치 전 감사에서도 있는 것으로 보고 NOTICES에 싣는다. 설치본 NOTICES의 Python 패키지 절은 그 트리의 Python을 스캔해 만든다(설치된 집합 = 감사 기준 집합 + Kookabug 패키지). JavaScript 절은 앱 번들에 든 prod 의존성과 글꼴이다. 어느 쪽이든 읽을 수 없는 폴더는 실패다(그 안을 판정하지 못했으므로). 모델 표의 경로는 모델 폴더 안 상대 경로만 받는다
  - **numpy 한정 예외**: numpy의 OpenBLAS DLL에 정적으로 들어간 GCC 런타임(`GPL-3.0-or-later WITH GCC-exception-3.1`)은 numpy 패키지에서만 허용한다(GCC Runtime Library Exception). 거부 패턴보다 먼저 보되 다른 패키지에서 같은 식이 나오면 금지 그대로다. NOTICES에 예외와 이유를 적는다
- 코드 서명: SignPath(오픈소스용) 신청. 자동 승인되지 않고, 남이 만든 바이너리(Python, uv)를 재서명하는 데 제약이 있으므로 서명 범위를 신청 때 확인한다. 서명 전까지는 SmartScreen 경고를 문서로 안내한다
- M1 완료 기준에 "Python 없는 깨끗한 Windows에서 설치·실행"이 들어 있다. 배포는 마지막에 붙이는 일이 아니다

## 5. 캡처·입력·비전

| 영역 | 결정 |
|---|---|
| 캡처 | **WGC**(창 단위)를 먼저 완성한다. DXGI는 검증된 뒤 **명시적으로 고르는** 선택 경로로 추가한다. 검은 프레임만 보고 백엔드를 자동으로 바꾸지 않는다 (검은 로딩 화면은 정상일 수 있고, DXGI는 모니터 단위라 위에 겹친 다른 창을 찍는다). 백엔드 선택은 사전 기능 검사와 명시적 API 오류로만. PrintWindow·BitBlt 자동 폴백은 이후 버전. **WGC는 화면이 바뀔 때만 프레임을 준다**: 창 바인딩마다 세션 하나가 최신 프레임을 들고 있고, 캡처 요청은 50 ms 동안 새 프레임을 기다린 뒤 오지 않으면 최신 프레임을 이 관측으로 **재사용**한다(세션이 살아 있고, 첫 프레임을 받았고, 바인딩이 살아 있고 최소화 아니고, 지금 창 크기·DPI가 그 프레임과 같을 때) — 멈춘 화면은 오류가 아니다. 단 캡처가 최소화를 본 뒤 복원을 확인하면 세션을 다시 연다(옛 세션 프레임은 최소화 확인 뒤 늦은 콜백·애니메이션일 수 있고, CI에서 WGC가 복원 뒤 5초 동안 프레임을 주지 않아 최소화 중 바뀐 화면 대신 옛 화면을 재사용했다). 장애 구분: 첫 프레임이 기한 안에 안 옴 → `capture_timeout`, 크기·DPI가 바뀌었는데 맞는 프레임이 안 옴 → `capture_timeout`(0.25초 안에 안 오면 세션을 한 번 다시 열어 첫 프레임을 받는다 — windows-capture는 크기가 바뀐 프레임을 버리므로 멈춘 화면은 새 크기 프레임을 주지 않는다), 세션 종료·콜백 예외 → 한 번 다시 만들고 그래도 안 되면 `capture_failed`, 창 닫힘 → `window_gone`, 최소화 → `window_minimized`, 세션 생성 실패 → `capture_unsupported`. 0.25초는 그 세션이 불일치를 처음 본 때부터 재므로 짧은 노드 기한의 요청이 이어져도 다시 열기가 진행되고, 다시 연 세션의 첫 프레임 대기도 다음 요청이 이어받는다. 설정 기한 안에 프레임을 못 준 세션은 버린다(노드 기한이면 둔다). 세션 시작처럼 끊을 수 없는 호출 뒤와 결과 확정 직전에 취소·기한을 다시 보아, 기한 뒤에 준비된 프레임을 성공으로 내보내지 않는다. 창이 닫히면(`on_closed`·파괴 이벤트) 그 세션의 픽셀을 다시 캡처하지 않아도 바로 놓고, 네이티브 세션은 다음 캡처·`close`·실행 끝 회수에서 실제로 멈춘다(`close`는 멈추고 끝나기까지 확인해야 성공). 사망 알림은 콜백·추적기 스레드에서 오므로 서비스 잠금을 기다리지 않고 큐로 넘기며, 서비스 잠금 안에서는 상태만 바꾸고 네이티브 세션 멈추기(콜백 스레드 join)는 잠금 밖에서만 한다 — 시작 중 종료·회수 중 종료가 서로 기다리지 않게. 프레임은 확장 프레임 경계 크기이므로 클라이언트 영역만 잘라 쓴다(커서·테두리 끔). 자른 픽셀은 자기 메모리를 가진 복사본이다 — 뷰는 전체 프레임 할당을 붙잡아 저장소 예산을 속인다. 장시간 검사(`soak`, 로컬 필수): 세션 200회·크기 변경 500회·캡처 10,000회에서 핸들 증가 ≤ 50, 스레드 ≤ 2, 개인 바이트 ≤ 64 MiB, 모든 세션 종료 — WGC 세션을 열 때마다 남는 `ALPC Port` 핸들(windows-capture·WGC 쪽, 세션당 최대 하나)은 따로 센다 |
| 프레임 정보 | 프레임마다 백엔드, 대상 창(바인딩), 클라이언트 크기·화면 원점, DPI, 캡처 영역, 프레임 번호, 재사용 여부와 **시각 두 개**를 붙인다: `observed_at`(이 요청이 관측으로 확정된 시각 — 판정·기록이 "이 시점의 화면"으로 쓰는 값)과 `pixels_at`(그 픽셀이 WGC에서 온 시각). 프레임 번호는 프로세스 안에서 유일해 다른 창·다시 만든 세션의 프레임과 섞이지 않는다. 백엔드가 바뀌면 기존 관측값은 무효 |
| 입력 | SendInput. 입력 직전(누르기·글자·이동·휠마다, **떼기·전부 떼기·복구에는 하지 않음** — 떼기까지 막으면 복구가 막힌다) 창 유효성·최소화·포그라운드·점 아래 창·권한 수준·입력 데스크톱 확인. **포그라운드**(키보드·글자) = 포그라운드 창이 대상 창 자신이거나 대상 창이 (소유자 사슬로) 소유한 팝업. 같은 프로세스의 독립 최상위 창은 거부(`window_not_foreground`). **점 아래 창**(마우스) = 클릭 화면 점의 창을 부모 사슬(`GA_ROOT`)로 올린 최상위 창이 정확히 대상 창. 대상 창의 소유 팝업이 덮은 지점도 거부(`point_obscured`) — WGC 창 캡처에는 소유 팝업이 찍히지 않아 관측과 입력 대상이 어긋난다. 팝업을 누르려면 그 팝업을 대상 창으로 붙인다. 게임 무결성 수준이 runner보다 높으면(토큰을 읽을 수 없는 경우 포함) `target_elevated` — UIPI가 입력을 조용히 버리므로 관리자 권한 터미널에서 실행하라고 안내 (자동 권한 상승 없음). 잠금 화면·UAC 화면이면 `input_desktop_unavailable`. **우리 입력 표식** (M4): 우리가 보내는 모든 입력(키·글자·마우스, 떼기·전부 떼기, 첫 창 앞으로 가져오기의 Alt, 얻기·감독자 복구의 떼기)은 `dwExtraInfo`에 고정 표식 `KOOKABUG_INPUT_MARK`를 싣는다 — 녹화 훅이 그 입력을 사람 입력과 구별해 버린다(검사 도구의 입력도 기본은 같은 표식) |
| 창 | 창 찾기는 제목(대소문자 무시 부분 일치, `/정규식/`)·실행 파일 이름·PID, 보이는 최상위·소유자 없는 창(소유 팝업은 명시적으로)·`cloaked` 제외, Z 순서 앞. 띄운 게임의 창은 실행 Job 안 모든 프로세스에서 찾는다(런처형). **창 수명 추적**: runner가 창을 정할 때 바인딩(hwnd·PID·프로세스 생성 시각·실행 안 ID)을 만들고, 창 파괴 이벤트(`EVENT_OBJECT_DESTROY`)나 WGC 세션 종료가 오면 그 바인딩은 죽는다 — 같은 프로세스가 같은 hwnd 값으로 새 창을 만들어도 옛 참조는 `window_gone`. 파괴 이벤트는 비동기라, 파괴와 이벤트 도착 사이 수 ms 안의 같은 hwnd 재사용은 막지 못할 수 있다(문서화된 한계). 지원하지 않는 조건은 정해진 오류 코드로 끝난다(`window_gone`·`window_minimized`·`window_not_foreground`·`point_obscured`·`window_mismatch`·`target_elevated`·`input_desktop_unavailable`·`dpi_awareness_unavailable`·`launch_failed` 등, 메시지에 대상 창·지금 앞에 있는 창) |
| DPI | runner 진입점 첫 줄에서 프로세스를 Per-Monitor V2로 정하고 확인(이미 다른 수준이면 `dpi_awareness_unavailable`). 캡처·입력 좌표의 단일 기준은 **대상 창 클라이언트 영역 물리 픽셀**: 정규화 사각형은 그 순간 클라이언트 크기를 곱하고(네 변 각각 반올림), 화면 좌표는 입력 직전에만 만든다. 창 함수는 좌표를 읽는 동안 그 스레드만 PMv2로 두어 프로세스 수준과 무관하게 물리 픽셀을 본다. 감독자는 좌표를 쓰지 않으므로(복구의 떼기만) 프로세스 수준을 바꾸지 않는다 |
| 이미지 매칭 | OpenCV `matchTemplate`(TM_CCOEFF_NORMED) + 멀티스케일 + 색 확인 |
| OCR | 엔진 교체 가능(`kookabug.json` `ocr.engine`, M1 값 `rapidocr` 하나). **기본 RapidOCR**(ONNX Runtime CPU): RapidOCR 3.10의 검출(DB)·인식(CTC) 전후처리를 옮기고 방향 분류는 하지 않는다. **검출 크기 정책**(`DetConfig`, `kookabug.json` `ocr.det`로 바꿀 수 있음): 검출 모델은 입력 픽셀이 많으면 작은 글자를 놓친다(실측: 작은 글자 하나가 1024×640까지는 거의 다 잡히고 1024×1024·1920×1080에서는 거의 못 잡힘, 줄여 넣으면 더 놓침). 그래서 1024×640 픽셀까지는 한 번에, 넘으면 원래 해상도로 640 정사각 타일(겹침 128)마다 검출하고, 타일 경계에서 잘린 상자·겹친 곳의 같은 상자를 합친다. 겹침보다 큰 글자는 전체를 1024×640 픽셀로 줄여 한 번 더 검출해 잡는다. 검출 입력은 짧은 변이 64보다 작을 때만 늘리고(RapidOCR 기본 736은 작은 영역을 열 배 넘게 키워 1초 넘게 걸리고 글자가 깨짐 — PaddleOCR 3.x 검출 기본값), 긴 변 4096이 넘을 때만 줄인다(4K는 그대로). 낮고 긴 한 줄 영역의 세로 여백은 타일마다 붙인다. 화면 전체 읽기는 느리다(측정: 1024×640 약 0.4~0.7초, 1920×1080 약 1.5초, 3840×2160 약 4~5초) — 노드는 영역을 주는 것이 기본이다. 관측 한 번의 유효 기한에 설정 기한(`run.capture_timeout_ms`, 기본 2000)이 들어가므로, 큰 화면 전체를 읽는 그래프는 그 설정을 읽기 시간보다 크게 잡아야 한다(노드 timeout만 늘려서는 설정 기한을 넘지 못하고 `capture_timeout`, 엔진은 기한을 늘리지 않는다). 모델은 검출 `PP-OCRv6_det_small`·인식 `korean_PP-OCRv5_rec_mobile`(사전은 ONNX 메타데이터) 두 개를 `ocr/models.toml`에 주소·SHA256·크기·라이선스·근거 원문(PaddleOCR `LICENSE`, RapidOCR `MODEL_LICENSES.md`)으로 고정하고, git에 넣지 않고 `tools/fetch_ocr_models.py`가 받아 확인한다(CI는 캐시). 찾는 순서는 `KOOKABUG_OCR_MODELS`(주면 그 폴더만) → 설치본 `ocr-models/` → 레포 `build/ocr-models/`, 없으면 `ocr_model_missing`, 해시가 다르면 `ocr_model_corrupt`. **실행 중에 내려받지 않는다**. 추론 한 번은 끊을 수 없어 시작 전·추론마다 직전과 끝난 바로 뒤(결과를 후처리에 넘기기 전)에, 그리고 검출 후처리 윤곽 16개마다·타일 상자 합치기(이웃만 비교, 상자 1200개 약 20 ms) 비교 256번·판정 64번마다·상자 자르기마다 취소·기한을 보고 넘었으면 결과를 버린다 — 노드 timeout은 최대 추론 한 번만큼 늦는다(측정: 타일 검출 한 번 약 0.1초, 한 번에 검출하는 1024×640 약 0.3~0.4초, 인식 묶음 한 번 0.4초 이하). **엔진 준비(모델 확인·세션 만들기)는 관측 기한에도 노드 기한에도 넣지 않는다**: runner는 OCR 노드를 쓰는 실행의 시작 때 백그라운드로 준비하고, 실행기는 코어 OCR 노드 함수를 부르기 전(노드가 자기 기한을 만들기 전)에 그 준비를 취소·전체 기한만 보며 기다린다(`PreparingPlatform.before_node`) — 대기 노드는 준비 뒤 자기 `timeout_ms`를 온전히 받는다. 플러그인 노드의 읽기는 첫 읽기에서 같은 방식으로 기다려 설정 기한은 먹지 않지만, 노드가 이미 만든 기한은 그대로 간다. onnxruntime 스레드 풀의 바쁜 대기는 끄고, runner는 Windows 실행 속도 제한(EcoQoS)에서 빠진다 — 로컬 재현에서 창 없는 뒤쪽 프로세스의 읽기가 열 배 넘게 느려진 원인 후보다(M1·M2 Sandbox 설치 확인 반영, 원본 Sandbox 재확인 전). **Windows OCR은 선택 백엔드**: Microsoft가 데스크톱에서 패키지 ID를 요구하므로, 지원 조건을 확인한 환경에서만 켠다. Tesseract는 넣지 않는다. 한국어 모델의 정확도·속도는 M1에서 예제 게임(`fixtures/sample-game/ocr-samples`)과 실제 게임 폰트로 `tools/ocr_bench.py`가 측정한다 |

| 단계 | 구현 |
|---|---|
| M0b | 기록 API 하나로 모든 스크린샷·영상·OCR 텍스트를 저장한다. 노드가 파일을 직접 쓰지 않는다. secret 입력 노드 자동 생략, 상위 off 우선, 생략 이유 기록. 예외 시 스크린샷(SDK)도 이 API를 거친다 |
| M1 | 실제 캡처에 연결. `sensitive` target의 OCR 결과 secret 처리 |
| M3 | 영상: 실행 중 임시 파일로 계속 기록 → 성공하면 지우고 실패하면 보관(`failed_only`). 기록 끈 구간은 영상도 멈춘다. 중단된 실행의 임시 영상은 감독자가 마무리한다. **게이트**: 열린 스텝 스택(호출 스택) 전체 중 하나라도 실효 `video: off`이거나 비밀값 입력 스텝이면 off, 멈춘 동안 off. 스텝마다 `step.start` 전에 보류 차단(새 픽셀 없음, 조각은 자르지 않음) → 입력 계산·비밀값 분류 뒤 정함. 녹화 스레드는 가져오기 전후로 게이트를 보고 그 사이 차단이 시작된 프레임을 버린다. **격자**: 5 fps, 칸마다 그 칸에 받은 가장 새 프레임(없으면 직전 반복) — 재생 위치 `k × 200 ms` = 실행 시각 `t0 + k × 200 ms`. **조각**: 한 모드·한 창·한 크기·최대 60초, off·모드·창·크기 변화·반복 2초 초과에서 닫음, 쓰는 중 `.part.mp4`. **보관**: 최종 `run.end`로 `fail`·`error`면 `failed_only` 조각을 남기고 `pass`·`skipped`·사용자 취소면 지움. 워크스페이스가 `record.video`를 정하지 않으면 `failed_only`다. 인코더 열기 시험(차가운 MF 첫 열기 약 0.6~1초)은 runner를 시작하자마자 띄우고(연결·기록 시작·스냅샷과 겹침), 영상이 꺼지지 않은 실행(기본 정책이 `off`가 아님)은 **시험이 끝난 뒤 첫 스텝을 시작한다** — 상한 20초 또는 남은 기한의 절반, 기다리는 동안에도 취소·기한을 본다. 상한을 넘기면 녹화 스레드가 시험을 기다리는 동안 프레임을 메모리에 모았다가(칸마다 한 장, 256 MB 상한 — 전체 HD로 몇 초, 차단·창 없음이 끼면 그 앞은 버림, 게이트가 바뀌면 실시간 루프처럼 바로 깸) 시험이 끝나면 그 시각 그대로 조각에 쓴다. 모은 프레임을 쓸 때는 프레임마다 그 직전의 최신 게이트 off 구간 이력을 실시간 루프와 같은 반영 함수로 받아, 그 프레임 전에 시작한 구간을 먼저 반영하고(조각은 off 구간 시작에서 닫힘) 구간 안 프레임은 쓰지 않는다. 반복 칸 채우기는 채울 때마다 게이트의 최신 차단 이력(보류 중이면 보류 시작, 아직 비우지 않았거나 열린 off 구간이면 그 시작)을 넘지 않는다 — 인코더 열기처럼 오래 걸리는 일 사이에 확정된 차단도 반복 칸이 덮지 않는다. 실행이 시험보다 먼저 끝나 모은 것이 있으면 run.end 뒤 **영상 마무리 단계**(3장 "하드 종료" 아래, 상한 30초)가 시험을 더 기다려 쓰고, 상한 초과·취소·감독자 사망·하드 종료면 `status: omitted`/`encoder_not_ready`로 남긴다 — 그래서 준비가 늦고 실행 기한이 짧아도 짧은 실패 실행의 영상이 마무리 기한(녹화 기다림 3초)에 막혀 조용히 사라지지 않고, 실행 기한·판정·종료 코드·`failed_only` 지우기·디스크 상한은 그대로다. `starting` 빈 구간은 모은 프레임이 없던 앞부분뿐이다. **작성자 종료 확인 뒤 마무리**: runner는 녹화 스레드를 실제 시간 3초 기다려 끝났을 때만 `finalize_video`를 부른다. 기다림은 처음 보낸 `runner.stopping`부터 재고, 실제로 적용되는 가장 이른 종료 기한(외부 취소의 감독자 타이머·감독자 사망 + 유예·`runner.stopping` + 유예)에서 기록 여유 1초(유예 2초 미만이면 유예의 절반)를 뺀 때를 넘지 않는다(3장 "하드 종료"). 그 안에 안 끝났으면 영상을 포기(`run.end.omitted` `video`/`encoder_stuck`)하고 `video/`를 건드리지 않는다 — runner 종료를 확인한 감독자가 지운다. 녹화 스레드가 늦은 인코더 대기 중이면(멈춘 것이 아님) 포기하지 않고 run.end 뒤 영상 마무리 단계로 넘긴다 |

## 7. MCP 도구

core 툴셋만 항상 켜고, 나머지는 `kb_toolset_enable`로 켠다.

| 툴셋 | 도구 |
|---|---|
| core | `kb_project_info`, `kb_toolset_enable`, `kb_graph_list`, `kb_graph_get`, `kb_graph_validate`, `kb_node_search`, `kb_run_status`, `kb_log_search` |
| graph_edit | `kb_graph_create`, `kb_graph_patch`(노드 추가·수정·삭제·연결 연산 묶음, 기준 revision 필수), `kb_target_create`(스크린샷에서 자르기) |
| run | `kb_run_start`(중복 방지 키), `kb_run_cancel`, `kb_run_events`, `kb_run_artifact_get`, `kb_run_compare`(M5, 지난 성공과 비교 — 조회) |
| observe | `kb_screen_capture`, `kb_image_find`, `kb_ocr_read` |
| control | `kb_input_click`, `kb_input_key`, `kb_input_type`, `kb_app_launch` (입력 임대권 필요) |
| screens | `kb_screen_list`, `kb_screen_get`, `kb_screen_save`(M7) |

**권한 프리셋** (기본 `graph_author`). 조회 도구 = 읽기만 하는 도구. 판정 순서는 [[워크스페이스 구조]] "에이전트 권한"

| 도구 | `read_only` | `graph_author` | `runner` | `full` |
|---|---|---|---|---|
| core 전체 (조회) | allow | allow | allow | allow |
| graph_edit 전체 (변경) | deny | ask | ask | allow |
| `kb_run_start`, `kb_run_cancel` (변경) | deny | deny | allow | allow |
| `kb_run_events`, `kb_run_artifact_get` (조회) | allow | allow | allow | allow |
| observe 전체 (조회) | allow | allow | allow | allow |
| control 전체 (변경) | deny | deny | ask | allow |
| `kb_screen_list`, `kb_screen_get` (조회) | allow | allow | allow | allow |
| `kb_screen_save` (변경) | deny | ask | ask | allow |

툴셋 값(`allow`·`ask`·`deny`)을 주면 그 툴셋의 변경 도구에 그 값을, 조회 도구에는 `deny`일 때만 `deny`를 쓴다.

- 서브그래프를 도구로 노출할 때는 안쪽 노드가 쓰는 권한을 합쳐서 검사한다
- `kb_graph_patch`는 노드 ID를 바꾸는 연산을 받지 않는다
- **Agent 판단 노드**(`cli_judge`, `api_judge`)가 부르는 에이전트에는 Kookabug 제어 도구를 주지 않는다. 이미지와 질문만 준다. 에이전트 패널의 Agent와 실행 환경을 분리한다

### M0b 구현 반영

| 바뀐 것 | 이유 |
|---|---|
| 권한: 판정 대상은 에이전트, 정책 세 계층(사용자 설정·`local.json`·`kookabug.json` 팀 상한), 7장 "기본 권한" 열을 프리셋 4개 표로 바꿈(기본 `graph_author`는 `kb_run_start`가 deny), 잘못된 권한 설정은 에이전트 거부 (3장 계약, 7장) | 툴셋 하나에 값 하나로는 "편집은 묻고 실행은 막는다" 같은 조합과 팀이 정한 한도를 표현하지 못한다. 사람이 쓰는 CLI까지 막으면 권한 설정 실수로 사람이 아무것도 못 한다. 권한 파일이 틀렸을 때 기본값으로 돌아가면 팀이 막은 것이 조용히 풀린다 |
| Job Object·뮤텍스를 pywin32 대신 ctypes로 (5장 표), 실행 Job은 감독자가 만들고 runner가 이름으로 열어 자기를 넣는 두 핸들 (3장 "프로세스 정리") | 런타임 의존성·라이선스 감사 항목이 늘지 않는다. 감독자 핸들 하나뿐이면 감독자가 죽는 순간 runner까지 끝나 키 해제·기록 마무리를 할 주체가 없다 |
| 입력은 runner의 입력 액터 하나만 보낸다(3장 계약), 취소 순서 1·2를 "액터 게이트 닫기"·"액터 큐 맨 앞 release_all"로, 입력 임대권에 전용 스레드·얻을 때 앞 소유자 복구·복구 표시 파일·깨끗한 놓기 조건·감독자 복구도 임대권 안·이중 고장 처리 (3장 "입력 임대권") | 취소를 받은 스레드가 직접 키를 떼면, 임대권을 놓은 뒤 늦게 도착한 떼기가 다음 소유자의 입력을 건드릴 수 있다. 앞 소유자가 남긴 키를 다음 소유자가 입력 전에 떼야 "감독자의 늦은 복구"와 "다음 실행의 입력"이 겹치지 않는다. 뮤텍스의 ABANDONED는 다른 핸들이 열려 있을 때만 보이므로 복구 여부는 옆 파일로 정한다 |

| 워커: 코어 노드는 runner 안·플러그인 노드는 워커, 입력·캡처는 runner가 하고 워커 `ctx` 요청은 선언으로 다시 검사, 시작 순서 "스냅샷 → hello·원격 등록 → 검증", `ctx.path()`는 실행 스냅샷 기준 (3장 계약 "워커") | runner가 플러그인 코드를 import하지 않으므로 원격 노드 선언을 검증 전에 hello로 받아야 한다. 코어 순수 노드까지 RPC로 부르면 소비마다 왕복이다. 입력 주체를 runner 하나로 둬야 단일 생산자 계약이 지켜지고, 원본 경로를 읽으면 실행 도중 바뀐 파일을 읽는다 |

### 마무리 수명 반영 (2026-11-04, CI 수정 5 검수)

| 바뀐 것 | 이유 |
|---|---|
| 판정 확정(주 스레드 마무리 시작) 뒤에는 제어기의 전체 기한 감시를 끝낸다. 마무리의 실제 시간 유예·감독자 사망 감시·외부 취소는 그대로이고, 마무리 시간도 경과·활성 경과에 그대로 든다 (3장 "기한 감시") | 녹화 정리(인코더 닫기)가 길면 이미 정해진 pass에 `cancel.requested(deadline_exceeded)`·`cancel_reason`이 붙었다. 마무리는 판정을 바꾸지 않으므로 기한 취소 대상이 아니다. 경과 기록을 줄여 피하면 "`duration_ms`는 실제 경과"가 깨진다 |
| 녹화 스레드 기다림을 처음 보낸 `runner.stopping`부터 3초로 하되, 실제로 적용되는 가장 이른 종료 기한(감독자가 `run.cancel` `hard_stop_at_mono`(+ `hard_stop_in_ms`)로 알린 하드 종료, 감독자 사망 + 유예, `runner.stopping` + 유예)에서 기록 여유를 뺀 때를 넘지 않게 한다. 기록 여유는 1초이고, 유예가 2초보다 짧으면 유예의 절반이다. 하네스 기본 유예는 제품 기본(5초)으로 맞춘다 (3장 "하드 종료", 6장 M3 행, rpc `RunCancelParams`) | 감독자 하드 종료는 `runner.stopping` + 유예에 나는데, runner는 그 뒤에 녹화를 3초 기다린 다음 `run.end`·`run.json`을 썼다. 그래서 유예가 3초면 영상 포기 경로와 하드 종료가 겨뤄 runner가 exit 4로 끝났다. 외부 취소는 감독자가 요청을 보내기 전에 타이머를 걸고, 감독자 사망은 감시자가 알아챈 때부터 유예를 잰다. 그래서 runner가 취소를 늦게 처리하면 `runner.stopping` 기준 예산이 실제 기한보다 늦다(검수 재현: 1.3초 지연·유예 3초에서 exit 4). 유예는 사용자가 정할 수 있으므로(최소 1 ms), 설정을 4초 이상으로 묶지 않고 runner가 남은 예산 안에서 기다린다. 먼저 건 타이머는 미루지 않는다. 기한은 절대 단조 시각(`hard_stop_at_mono`)으로 넘긴다. 같은 PC의 `time.monotonic`(QPC)은 프로세스 사이 원점이 같다는 것이 계약이다. 남은 시간(ms)만 넘기면 송신·수신·처리 지연만큼 기한이 늦게 잡히고 그 지연에는 상한이 없다(검수 재현: 송신 전·수신 처리 전 1.3초 지연에서 exit 4). runner는 절대 시각과 꺼낸 시각 + 남은 시간 중 이른 쪽을 쓰고, 절대 시각이 말이 안 되면(이미 지남·유예보다 멂 = 원점이 다르다고 봄) 녹화를 기다리지 않고 바로 기록한다 |
| 마무리의 기다림(워커 종료·액터 멈춤·녹화 스레드)을 고정 예산 대신 그때의 가장 이른 종료 기한 − 기록 여유까지로 한다. 제어기가 종료 기한이 바뀔 수 있는 때(`run.cancel` 기한 수신·취소 시작·`runner.stopping`)에 기한 갱신 신호(Event)를 세우면 녹화 기다림이 깨어 다시 잰다. 녹화 스레드가 끝날 때도 같은 Event가 선다. 끝을 신호로 받지 못하는 워커 프로세스·액터 스레드는 20·50 ms 단위로 나눠 기다린다 (3장 "하드 종료") | 정상 판정으로 녹화를 기다리기 시작한 뒤 외부 취소가 도착해 더 이른 기한이 알려져도, 한 번 정한 `join` 시간이 줄지 않았다. 검수 재현(유예 3초·멈춘 인코더·취소 송신 1.3초 지연·그 사이 pass)에서 6/6 exit 4로 pass를 잃었다. 하드 종료 타이머를 늦추거나 마무리 중 외부 취소를 무시하면 감독자의 종료 보장이 깨진다 |
